## 二、服务器配置

### 2.1 硬件

| 配置项 | 规格 |
|---|---|
| 实例 | 腾讯云 Windows Server 2022 |
| CPU/内存 | 4核 / 4GB |
| 系统盘 | **60GB SSD**（试验期暂不加数据盘）：系统 + SQL Server 程序 + SQL 数据/备份 + 应用全部落在 C 盘 |

> 内存 4GB 偏紧：**Express 版内存自动封顶约 1.4GB**（`max server memory` 配置对 Express 无效也无害），恰好不会撑爆 4GB 机器；Hangfire WorkerCount 已在代码设 1。
> 试验期无独立数据盘，60GB 系统盘空间紧张：**备份只保留 5 天并须定期拷走**（详见备份策略）；若数据库持续增长，正式推广前建议先加数据盘再迁移数据。Express 另有库大小上限 10GB——MES 试验期远达不到，可忽略。

### 2.2 软件环境

| 软件 | 说明 |
|---|---|

| .NET 8 Runtime / ASP.NET Core | API 运行（Hosting Bundle 或 runtime + ASP.NET Core 模块） |
| SQL Server 2022 **Express** | **已预装**，命名实例 `SQLEXPRESS`，Windows 认证（含 SQL 命令行工具 sqlcmd） |
| Nginx for Windows | 反代 + 静态（`C:\mes\nginx`，服务化经 NSSM） |
| NSSM | 非服务程序注册 Windows 服务（nginx / MES.API） |

### 2.3 网络端口（腾讯云安全组 + Windows 防火墙）

| 端口 | 方向 | 放行？ | 说明 |
|---|---|---|---|
| 80 | 入 | ✅ | http → https 跳转 |

## 三、Windows 部署步骤（主线）

### 3.1 软件安装（服务器）

1. **.NET 8 Runtime（ASP.NET Core）**：安装 `aspnetcore-runtime-8.0.x-win-x64.exe`（服务器只需 Runtime，无需 SDK）。
2. **SQL Server 2022（已预装 Express，通常跳过）**：目标服务器自带 Express（实例 `SQLEXPRESS`）。确认即可：`Get-Service | ? Name -like 'MSSQL$*'` 应见 `Running`、`sqlcmd -S localhost\SQLEXPRESS -E -Q "SELECT @@VERSION"` 应返回版本。若某台机器确实没装 SQL，才走图形安装（默认实例 / **Windows 身份验证模式** / 仅数据库引擎），并确认 sqlcmd 可用。数据与备份由脚本放到 C 盘 `C:\MSSQL`。
3. **工具**：nginx 解压后把**内容**拷到 `C:\mes\nginx\`（nginx.exe 直接在它下面）；nssm 解压后把 `nssm.exe` 放到 `C:\mes\tools\nssm\`。
4. **证书**：腾讯云 SSL 证书 → 申请免费 DV（域名 `zhz.js.cn`）→ 下载 **Nginx 版**（含 `.crt` 与 `.key`）→ 放到 `C:\mes\nginx\conf\ssl\`。

> 本节由脚本 `scripts/deploy-windows/01-prepare.ps1` 辅助完成。

### 3.2 数据库初始化（必须最先，先于 API 启动）

> ⚠️ **必须先建空库**：`MES.Api` 启动时会自动执行迁移（`DatabaseMigrator` + `DbInitializer`）——但该逻辑只对「**已存在的库**」走标准全量建表。**若库不存在，启动会直接崩溃**（NSSM 将重启循环）。因此顺序是：先建库 → 再启 API。
> 空库建好后无需手动 `dotnet ef`，首次启动 API 自动完成全部建表 + 种子（46 角色 + 管理员 `Admin`）。

```powershell
# 以管理员打开 PowerShell；本机为命名实例 SQLEXPRESS（非默认实例）
# Express 内存自动封顶约1.4GB，无需手动锁内存；下面锁 2048 命令对 Express 无实际作用，执行也无害
sqlcmd -S localhost\SQLEXPRESS -E -Q "EXEC sp_configure 'show advanced options', 1; RECONFIGURE; EXEC sp_configure 'max server memory', 2048; RECONFIGURE;"
# 数据文件放 C 盘
sqlcmd -S localhost\SQLEXPRESS -E -Q "CREATE DATABASE MES ON (NAME='MES', FILENAME='C:\MSSQL\DATA\MES.mdf') LOG ON (NAME='MES_log', FILENAME='C:\MSSQL\DATA\MES_log.ldf')"
```
> 执行前确保 `C:\MSSQL\DATA` 目录存在。此步脚本：`scripts/deploy-windows/02-init-db.ps1`（已适配 `SQLEXPRESS`：自动发现实例服务账户授权、先连通实例再建库）。

### 3.3 发布（开发机执行）

```bash
# 开发机（本仓库根目录）
dotnet publish MES.Api     -c Release -o ./publish/api
dotnet publish MES.Blazor  -c Release -o ./publish/blazor
```
发布后**改写前端 API 基址为空（同源）**：把 `publish/blazor/wwwroot/appsettings.json` 的 `ApiSettings.BaseUrl` 改为 `""`（开发环境默认值是 `http://localhost:7000`，不可带上生产）。打包 zip → 拷贝到服务器 `C:\mes\`（RDP 或 pscp）。

> 脚本：`scripts/deploy-windows/03-publish-local.ps1`（含 BaseUrl 改写与打包）。

### 3.4 API 服务（NSSM 注册，服务器）

```powershell
# C:\mes\api 放 MES.Api 发布产物
nssm install MES.API "C:\Program Files\dotnet\dotnet.exe" "C:\mes\api\MES.Api.dll"
nssm set MES.API AppDirectory "C:\mes\api"
nssm set MES.API AppStdout "C:\mes\logs\api.out.log"
nssm set MES.API AppStderr "C:\mes\logs\api.err.log"
nssm set MES.API AppExit Default Restart
nssm set MES.API AppRestartDelay 5000
```
环境变量（NSSM `AppEnvironmentExtra`，`__` 表示配置节层级，与 `appsettings.json` 键对应）：
```
MES_CONNECTION_STRING=Server=localhost\SQLEXPRESS;Database=MES;Integrated Security=true;TrustServerCertificate=true;MultipleActiveResultSets=true
ASPNETCORE_URLS=http://127.0.0.1:7000
ASPNETCORE_ENVIRONMENT=Production
JwtSettings__Secret=<至少32位随机串，生产必改>
Seed__AdminPassword=<初始管理员密码，生产必改，仅首次建库生效>
Hangfire__Username=<非默认>
Hangfire__Password=<非默认>
CorsOrigins=https://zhz.js.cn
```
> ⚠️ **首次务必前台运行一次观察**（迁移+种子可能需几十秒）：
> ```powershell
> cd C:\mes\api
> $env:ASPNETCORE_URLS='http://127.0.0.1:7000'
> $env:ASPNETCORE_ENVIRONMENT='Production'
> dotnet MES.Api.dll
> ```
> 看到日志出现「已连接到数据库 / 迁移完成」且无异常后再 `nssm start MES.API`。

> 完整脚本：`scripts/deploy-windows/04-setup-api.ps1`。

### 3.5 Nginx（静态 + 反代）

- 前端发布产物拷贝到 `C:\mes\web\`
- `nginx.conf` 配置要点（完整模板见 `scripts/deploy-windows/nginx-mes.conf.template`）：
```nginx
server {
    listen 80;  server_name zhz.js.cn;  return 301 https://$host$request_uri;
}
server {
    listen 443 ssl;
    server_name zhz.js.cn;
    ssl_certificate     C:/mes/nginx/conf/ssl/zhz.js.cn_bundle.crt;
    ssl_certificate_key C:/mes/nginx/conf/ssl/zhz.js.cn.key;

    client_max_body_size 100m;                 # Excel 导入/导出大文件
    root C:/mes/web;                            # Blazor WASM 静态

    gzip on;
    gzip_types
        application/wasm
        application/octet-stream
        text/css
        application/javascript
        application/json
        image/svg+xml;

    location /api/ { proxy_pass http://127.0.0.1:7000; proxy_set_header Host $host; proxy_set_header X-Forwarded-Proto https; proxy_read_timeout 300s; }
    location /hangfire { proxy_pass http://127.0.0.1:7000; proxy_set_header Host $host; proxy_set_header X-Forwarded-Proto https; }

    # ── 缓存策略（2026-09-05 修复「手机/电脑永远加载旧 wasm、新 UI 不出现」）──
    # index.html / service-worker.js / appsettings.json 等 PWA 壳与运行时配置**非指纹**：
    # 一旦被长缓存，应用会一直拉旧版 wasm → 必须 no-cache。
    # 真正 .wasm/.dll/.css 下载自带 ?id=<hash> 指纹，_framework/、/css/、.br/.gz 规则长缓存不受影响。
    # 另：nginx「精确匹配 location = /path + add_header」对静态文件响应不可靠 → no-cache 统一放 location /。
    location / {
        try_files $uri $uri/ /index.html;        # SPA 兜底：/login、/orders 等深链与刷新不 404
        add_header Cache-Control "no-cache";
    }
    # boot.json / webassembly.js 也在 _framework/ 下但**非指纹** → 整目录重验证
    location /_framework/ { add_header Cache-Control "no-cache"; }
    location /css/        { add_header Cache-Control "public, max-age=31536000, immutable"; }
    location /icon-192.png { add_header Cache-Control "public, max-age=2592000"; }
    location /favicon.png  { add_header Cache-Control "public, max-age=2592000"; }
    # wasm 压缩孪生件(.br/.gz)必须回带 Content-Encoding，否则 Blazor loader 无法解压、启动即失败
    location ~* \.br$ { add_header Content-Encoding br   always; add_header Cache-Control "public, max-age=31536000, immutable" always; }
    location ~* \.gz$ { add_header Content-Encoding gzip always; add_header Cache-Control "public, max-age=31536000, immutable" always; }
}
```
- 校验并注册服务：
```powershell
cd C:\mes\nginx && nginx -t
nssm install nginx "C:\mes\nginx\nginx.exe"
nssm set nginx AppDirectory "C:\mes\nginx"
nssm set nginx AppExit Default Restart
nssm start nginx
```
> ⚠️ **代码侧配套**：`MES.Api/Program.cs` 已加入 `UseForwardedHeaders`（仅信任 `127.0.0.1`），配合 `proxy_set_header X-Forwarded-Proto https`，生产 `UseHttpsRedirection` 不会把反代请求误判为 http 造成 307 循环。**反代与 API 必须在同一台机器（回环）**。

> 脚本：`scripts/deploy-windows/05-setup-nginx.ps1`。
>
> ⚠️ ① **模板源 `scripts/deploy-windows/nginx-mes.conf.template` 必须保持纯 ASCII（无中文注释）**：05 脚本用 `Get-Content -Raw`(默认 ANSI/GBK) 读模板 + `Set-Content -Encoding ASCII` 写 conf，模板里任何中文注释都会被误码并**吞掉换行**、把下一行 location 并入注释 → 规则静默丢失或 `"location" directive is not allowed here`。文档正文（如上）可用中文，改 conf 前请勿把中文拷回 template。
> ⚠️ ② 改模板重跑 05 后必须 **`Restart-Service nginx`**：nssm 注册的 nginx 在 Session 0，`nginx -s reload` 报 `OpenEvent(...) failed (5: Access is denied)` 不生效，只有重启服务才加载新配置。

## 四、上线后增量更新

### 4.1 数据库双库模型（正式启用前提）

> 适用说明：当前部署为**试验期**——云库 `MES`（zhz.js.cn）是从真库 `zhou/MESMN` 备份恢复来的副本，存的多是模拟数据；代码演化（迁移、种子）都发生在真库。**正式启用后角色反转**：云库承载真实业务数据、成为**生产权威**；本地真库退化为**种子源与迁移制造地**。本章增量更新步骤即正式期模式。

| 阶段 | 本地真库 `zhou/MESMN` | 云库 `MES`（zhz.js.cn） |
|---|---|---|
| 开发期（现在） | 权威：跑迁移 + 种子 + 开发/模拟数据 | 副本：从真库备份恢复（`08-restore-db.ps1`），测试用 |
| 正式启用后 | 退化：新种子/新迁移的演化场地（升级包制造者） | **生产权威**：承载真实业务数据 |

**正式启用切换（整库恢复仅此一次）**
1. 真库整理成「干净骨架 + 正式种子/基础档案」终态：清模拟数据；系统配置类种子写进 DbInitializer（幂等）或新增 `Seed*` 迁移，业务档案走数据工具导入（预览 / 校验 / 整批回滚）；
2. 真库全链路冒烟（登录 / 建单 / 打印 / 计件试算）；
3. 真库 `BACKUP` → 传服务器 → `08-restore-db.ps1` 恢复云库（模拟数据被整库替换为正式库）；
4. 同批发新代码（api + web）；云库启动自动 Migrate + 幂等 seed（库已完整 → 无 pending 空转安全）→ 冒烟上线。

> ⚠️ 与第 3.2 节的差别：**本项目的正式/试验建库一律走「真库备份恢复」（`08-restore-db.ps1`）**，不是 3.2 描述的空库自建——EF 迁移链无法自建空表（`InitialCompressed` 为聚合空壳），见 `14_部署执行单.md` 第 7 步实证。

**正式期三条硬纪律**
1. **禁止再用「真库备份整库覆盖云库」**——会把生产数据抹成开发库；`08-restore-db.ps1` 只在切换点用一次，之后退出。
2. **云库结构升级 = 增量迁移**：云库表结构 + `__EFMigrationsHistory` 完整，能接住新迁移。发布路径 = 新代码到云 → 启动自动 Migrate 只应用新增 pending（配合下方 4.3「新 API 先跑」）。⚠️ **切换后的新迁移必须对生产安全**：纯结构变更 + 幂等种子（`Any()` / 键守卫）；**禁止夹带面向开发模拟数据的一次性回填 SQL**（如开发期 5000 行回填、OPENJSON 改写），那些只该在真库执行。
3. **备份从「建议」升级为「必须」**（详见[五、备份策略](#五备份策略)）：服务器内每日计划任务只是底线，正式数据须**定期异地拷走 `.bak` + 定期恢复演练**，确保真实数据救得回。

### 4.2 核心原则

| 原则 | 说明 |
|---|---|
| **数据库只加不减** | 只 `AddColumn` / `CreateTable`，禁止 `DropColumn` / `RenameColumn` |
| **新代码不动旧代码** | 新功能用新文件，不改已上线接口签名 |
| **API 向前兼容** | 响应只加字段不删字段 |
| **回滚只回滚代码** | 数据库迁移不回滚（启动自动迁移会推进），代码重新覆盖旧发布产物即可 |

### 4.3 更新步骤（顺序不可颠倒）

1. **代码含新迁移时，先让 API 自动迁移**：新版本 API 启动时会自动应用待处理迁移（无需手动 `dotnet ef`），因此**先覆盖 API 并重启一次**，确认迁移成功。
2. **发布并覆盖产物**：
   - 开发机 `dotnet publish`（复用 `03-publish-local.ps1`）→ 拷贝 `api` 覆盖 `C:\mes\api`、`blazor` 覆盖 `C:\mes\web`（前端静态可先只覆盖 `wwwroot`，等版本一致再重启 API 也可）。
   - 建议覆盖前把旧产物归档到 `C:\mes\publish\<日期>\`（便于回滚）。
3. **重启服务**：
```powershell
nssm restart MES.API
# 前端为静态覆盖，无需重启 nginx；如改了 nginx.conf： C:\mes\nginx\nginx.exe -s reload -p C:\mes\nginx\
```
> 顺序铁律：**新 API 先跑一次（触发迁移）→ 再上同版本前端**，避免新前端调旧接口字段缺失。

### 4.4 回滚方案

```powershell
# 用归档产物覆盖回去即可（数据库不动）
# 前端：覆盖 C:\mes\web ；API：覆盖 C:\mes\api 后 nssm restart MES.API
```

## 五、备份策略

> 备份落在 C 盘 `C:\MSSQL\Backup`。本机为 **Express（无 SQL Agent）**，每日备份由 **Windows 计划任务**完成：运行 `scripts/deploy-windows/07-setup-backup.ps1` 一键注册计划任务 `MES_Backup_Daily`（每日 02:30 调 `backup-mes.ps1` → 压缩全量备份 + 清理 5 天前；日志 `C:\mes\logs\backup.log`）。
> 若日后升级为带 SQL Agent 的 Standard/Developer（默认实例），可改回 `scripts/deploy-windows/07-backup-job.sql`（SQL Agent 作业；**Express 不适用**）。
> ⚠️ **60GB 系统盘空间有限**：请**每周手动把 `C:\MSSQL\Backup` 里的 `.bak` 拷到系统外**（网盘 / 家里电脑）；正式推广加了数据盘后，把 `backup-mes.ps1` 里 `forfiles /d -5` 调回 `-30`，再重跑一次 `07-setup-backup.ps1` 即可放宽。

| 类型 | 频率 | 位置/保留 |
|---|---|---|
| 数据库全量（压缩） | 每日 02:30 | `C:\MSSQL\Backup\MES_FULL_yyyyMMdd.bak`，保留 5 天 |
| 数据库日志（可选） | 每小时 | 库默认简单恢复模式时无需；若切完整恢复再补 |
| 前端/API 发布归档 | 每次更新前 | `C:\mes\publish\<日期>\` |
| 证书 crt/key | 到期前手动续期 | 替换 `C:\mes\nginx\conf\ssl\` 后 `nginx -s reload` |

> 手动一次备份：`sqlcmd -S localhost\SQLEXPRESS -E -Q "BACKUP DATABASE MES TO DISK='C:\MSSQL\Backup\manual.bak' WITH COMPRESSION, INIT"`
> ⚠️ 每月至少做一次**恢复演练**（在临时库 RESTORE 验证），别等到要恢复才发现备份不可用。

## 六、正式期容灾与安全

> 本节承接第四章 4.1 双库模型：正式启用后云库承载真实数据，本节定义「数据安全 + 容灾」的落地组合。**原则一句话：备份异地化第一优先；第二台服务器等业务真需要「分钟级恢复」再上。**
> 目标指标（建议）：**RPO ≤ 1 天**（最多丢到最近一次每日备份）、**RTO ≤ 半天~1 天**（异地备份 + 快照 + 重建手册即可达成，无需双机）。

### 6.1 事故分级与对应手段

| 等级 | 事故 | 手段 | 优先级 |
|---|---|---|---|
| L1 | 误删数据 / 程序崩溃 | 每日备份 + 发布可回滚（见第四章） | 必有 |
| L2 | 单机硬盘损坏 | 备份**不在本机**（异地）+ 具备重建能力 | 必有 |
| L3 | 机房级灾难（整机没了） | 异地备份 + 重建材料齐备 | 必有 |
| L4 | 业务不容许停几分钟 | **双机 / 主备切换** | 视业务规模定 |

### 6.2 落地组合（无需第二台，即可压到小时级恢复）

| # | 动作 | 说明 |
|---|---|---|
| 1 | 重建「四件套」本地留档 | 发布产物（zip）+ 证书 crt/key + 服务环境变量清单 + 数据库备份 → 放本地/网盘。换服务器时照 `14_部署执行单` 可整体重建 |
| 2 | 线上库每日备份 + **异地副本** | 服务器计划任务每日 `.bak` 只是底线；**`.bak` 若只在服务器 = 等于没备份**（盘坏 / 机房故障全丢）。异地副本做法见 6.3 |
| 3 | 腾讯云 CVM 定时快照（可选但划算） | 整机级兜底：系统 / nginx / 应用配置一并救回，成本极低 |
| 4 | 季度**恢复演练** + 重建手册 | 每季度拿最新 `.bak` 到临时库/测试机 RESTORE 验证一次，别等真出事才发现备份不可用 |

> 3-2-1 原则：至少 3 份数据、2 种介质、1 份异地。对照上表自检「异地 + 演练」是否落实。

### 6.3 异地副本实现（按成本从低到高）

| 方案 | 说明 | 成本 |
|---|---|---|
| 腾讯云 **COS 对象存储**（推荐） | 服务器计划任务每日把 `.bak` 上传 COS（可开版本控制 / 生命周期自动清理） | 几元/月 |
| 本地电脑定时拉取 | 本地计划任务每日从服务器拉最新 `.bak`（网络可达时；不可达则用 COS 中转） | 0 |
| 每周 RDP 手动拷走 | 最简兜底（依赖人，易忘，不建议作为唯一手段） | 0 |

> 数据库备份属敏感数据：异地存放务必走**私有桶**（私有读写 + 临时密钥上传），勿用公有可读桶。

### 6.4 何时才上「第二台服务器」（双机 / 主备）

- **触发条件**：业务长大到「中断只能容忍数分钟 / 数据零丢失」——而不是「单机故障」或「机房灾难」（后两者靠 6.2 的异地备份 + 快照已足够）。
- **正确姿势**：届时把 **Express 升级 Standard**，做「从库只读 / AlwaysOn + 主备切换」，并配套域名 / DNS 切换。**不是**在单 Express 上硬凑主从镜像。
- **现状判断**：MES 为内部系统，停机半天~1 天可接受 → **现阶段不上第二台**，把 6.2 四件事做扎实即可。

> ⚠️ 双机并不消除备份需求：主备同步 ≠ 备份（误删、坏逻辑会照样同步到备机）。任何时候「异地备份 + 恢复演练」都不能省。
