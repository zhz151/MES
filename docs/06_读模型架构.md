# 读模型架构

**版本：V2.17**
**最后更新：2026-08-17**

## 1. 概述

项目中存在物化读模型（Materialized Read Model）的设计：将多张源表的数据聚合计算后，写入一张独立的汇总表，供列表页快速查询。

### 1.1 当前读模型

| 读模型 | 实体 | 刷新方式 | 状态 |
|--------|------|---------|------|
| 工单执行状况汇总 | `WorkOrderExecutionSummary` | 增量触发刷新（8个数据源 CRUD 时自动触发） | ✅ 活跃维护 |
| 订单列表汇总 | `OrderListSummary` | 增量触发刷新（订单 CRUD / 项次 CRUD / 产品要求 CRUD / 客户信息变更时自动触发） | ✅ 活跃维护 |
| 工单列表汇总（用料计划总览） | `WorkOrderListSummary` | 增量触发刷新（用料计划 CRUD / 工单生成修改 / 订单变更确认时自动触发） | ✅ 活跃维护 |
| 质量过程跟踪 | `QualityProcessTracking` | 增量触发刷新（成检到料/成品检验/入库/生产记录 CRUD 时自动触发） | ✅ 活跃维护 |

### 1.2 已移除的旧刷新服务 + 新增的增量刷新服务

**已移除的旧刷新服务：**

| 读模型 | 刷新 Service | 移除原因 |
|--------|-------------|---------|
| `OrderListSummary` | `OrderListSummaryService`（独立 Service） | 独立 Service 已移除，内联刷新保留在 `OrderService.RefreshByOrderIdAsync()` 中持续运行 |
| `WorkOrderListSummary` | `WorkOrderListSummaryService`（旧版） | 启动时全量 `RefreshAllAsync()` 浪费 DB 资源 |
| `WorkOrderStatusSummary` | `WorkOrderStatusSummaryService` | 启动时全量 `RefreshAllAsync()` 浪费 DB 资源 |

**新增的增量刷新服务（V2.0）：**

| 读模型 | 刷新 Service | 触发方式 |
|--------|-------------|---------|
| `WorkOrderListSummary` | `WorkOrderListSummaryRefreshService` | 按 SalesOrderNo 增量刷新（用料计划/工单/订单变更时自动触发） |

**此外，`OrderListSummary` 使用内联刷新（在 `OrderService` 中，非独立 Service）：**
| 读模型 | 刷新机制 | 触发方式 |
|--------|---------|---------|
| `OrderListSummary` | `OrderService.RefreshByOrderIdAsync()` | 订单/项次/产品要求 CRUD 时自动触发 |

**WorkOrderListSummary 刷新触发时机：**
- 用料计划 CRUD（7 种计划：圆棒穿孔/荒管采购/成品采购/库存使用/库料改制/在产改制/在产主工单）
- 工单生成（`GenerateWorkOrdersAsync`）
- 工单修改（`ModifyWorkOrdersAsync`）
- 订单状态变更确认（`CheckSalesOrderChangeAsync`）

所有增量刷新均为单级别（单 SalesOrderNo / 单 OrderId / 单 SalesOrderId）刷新，而非全量扫描。

## 3. WorkOrderExecutionSummary 详情

### 3.1 数据来源（8 张核心表）

| 表 | 用途 | 对应 Group |
|------|------|-----------|
| `WorkOrders` | 工单基础信息 | Group 1 |
| `PurchaseSemiPlans` | 原料采购计划 | Group 2 |
| `PurchaseFinishedPlans` | 成品采购计划 | Group 2 |
| `InventoryPlans` | 库存使用计划 | Group 2 |
| `RoundBarPiercingPlans` | 圆棒穿孔计划 | Group 2 |
| `ProductionBatches`（含 `ProcessGroups`） | 批次/投料数据 | Group 3, 4, 6 |
| `FinalInspections` | 成检次品数据（G21 次品总量，用于 G12 有效流转扣减） | Group 21, 12 |

辅助关联表：`SalesOrders`、`CustomerProfiles`（用于取客户名和业务员）。

### 3.2 当前刷新方式

**增量触发刷新（V2.4 起）**：不再需要用户手动点击刷新按钮，8 个数据源的 CRUD 操作触发 `TryRefreshExecutionSummaryAsync`（V2.7 起全部为 `await` 同步等待，V2.4-V2.6 为 fire-and-forget）：

```
源表 CRUD → TryRefreshExecutionSummaryAsync(workOrderNo)
  → 加载该工单号 + 同 SalesOrderNo 下所有兄弟工单
  → 批量加载 8 张源表的数据
  → 逐工单计算 Group 1-12 所有字段
  → 批量 Upsert 到 WorkOrderExecutionSummary 表
```

**触发覆盖（V2.7，全面 await 化）：**

| 触发源 | Service | 覆盖方法数 | 刷新模式 | 说明 |
|--------|---------|-----------|---------|------|
| WorkOrderService | 工单生成/修改/删除/状态变更 | 6 | `await` | GenerateFromOrderAsync, UpdateWorkOrdersAsync, UpdateStatusAsync, DeleteAsync, CheckAndUpdateWorkOrderStatusAsync, CheckAndUpdateWorkOrderStatusInternalAsync |
| MaterialPlanService | 7种用料计划所有CRUD | 14 | `await` | 通过内部 `RefreshReadModelAsync` 统一出口，单点接入 |
| PurchaseOrderService | 采购单所有CRUD | 7 | `await` | 通过 SourceWorkOrderNo 关联工单 |
| SubcontractOrderService | 分包单所有CRUD | 6 | `await` | 通过 SubcontractReturnItem.SourceWorkOrderNo 关联工单 |
| BatchService | 批次状态变更 | 2 | `await` | UpdateStatusAsync, UpdateBatchAsync |
| ProductionRecordService | 生产记录/委外/回收所有CRUD | 11 | `await` | 通过 BatchId→WorkOrderNo 关联工单 |
| InventoryService | 出入库/出库记录所有CRUD | 6 | `await` | OutboundAsync, BatchOutboundAsync, UpdateOutboundRecordAsync, HardDeleteOutboundRecordAsync |
| FinalInspectionService | 成品检验CRUD | 4 | `await` | 通过 ProductionBatchNo→WorkOrderNo 关联工单 |

**特点：**
- 增量刷新，仅刷新受影响工单 + 同 SalesOrderNo 下的兄弟工单（确保主号级聚合正确）
- V2.4-V2.6 fire-and-forget 模式，不阻塞业务操作；**V2.7 起改为 `await` 同步等待**，确保刷新完成后再返回（Fire-and-forget 在 Blazor Server/Scoped 环境下可能因 HttpContext 提前释放而丢失）
- 前端不再需要手动刷新按钮
- `POST /api/workorder-execution/refresh-all` 端点保留在后端，用于数据修复/初始化

**注意：**
- 兄弟工单刷新：同一 SalesOrderNo 下的所有工单都需刷新，确保主号级投料比/满足率/流转性等聚合字段正确
- 首次部署/数据修复时可通过 `RefreshAllAsync` 端点全量重建

**批次作用域原则（V2.12）：** WorkOrderExecutionSummary 中所有涉及批次数据的 Group（G11 原始投料、G13 合格流转、G14 返整执行、G21 次品总量、G15 成品入库等），在计算时必须使用**当前工单自身的批次集合**（`woBatches`），而非同主号下所有兄弟工单的批次集合（`batches`）。历史上 G8（过程不合格）和 G9（成检不合格）曾错误使用全族批次集合，导致跨工单数据污染（A 工单的 G8/G9 误包含了由 B 工单创建的 SplitFromNumber 批次的投料量），已修复（注：G8/G9 两组已随 V6.7 三组不合格删除）。

### 3.3 当前实时写入路径

用料计划保存时，`MaterialPlanService` 通过增量触发同时写回 `WorkOrder.MaterialPlanRate/MaterialPlanStatus` **和刷新 WorkOrderExecutionSummary**（双路同步）。

**G14 在产节点待量（PendingSection）：**
- G14 字段（9 个变形工序节点：荒管处理/在制修检/60冷轧/50冷轧/30冷轧/20冷轧/三辊冷轧/冷拔/附加成检）为实时计算字段。其中在制修检和附加成检不计入有效工序组数（不参与目标重量 2.5% 扣减），在 `RefreshAllAsync()` 中逐工单计算。
- **冷拔修正（V1.7）**：冷拔不再被视为单纯的"瞬时工序"而跳过量计算，现在与冷轧系列同等处理：当批次正在冷拔工段且 `CurrentSectionCompleted != true` 时，计入 PendingSectionDrawBench 待量
- 同时在 `DeformedProcessCompleted`（变形工序完成标记）计算中，冷拔与其他 5 项冷轧一并参与总和判定

**G13 字段说明：**
- G13 字段（IsUrging、IsBatchDelivery、IsPaused、AdjustmentRemark）**直接存储在 WorkOrderExecutionSummary 实体**中，由 `RefreshAllAsync` 从 `OrderDemandAdjustment` 同步写入
- 工单排程页面等列表页不再需要 LEFT JOIN `OrderDemandAdjustment`，直接从实体读取 G13 字段
- 当工单需求调整页面修改催单标记时，通过增量触发自动同步到 WorkOrderExecutionSummary

**生产流转性（ProductionFlowProperty）计算规则（V2.3 / V2.15 修订）：**
- 生产流转性基于 ScheduleStage（主号级，5 档）和 G13 字段计算，其中 IsUrging/IsBatchDelivery/IsPaused 采用**主号级聚合**（非工单级）：
  - `MainNoPaused` = 主号下**任一工单** `IsPaused==true`
  - `MainNoUrging` = 主号下**任一工单** `IsUrging==true`
  - `MainNoBatchDelivery` = 主号下**任一工单** `IsBatchDelivery==true`
- 判定优先级（V2.15 起随 ScheduleStage 五档全主号级调整，与代码一致）：
  ```
  IsPaused（主号级）                                                  → "暂停"
  Stage==3 || (Stage==2 && (MainNoUrging || MainNoBatchDelivery))    → "正常"
  Stage==2                                                            → "待料"
  Stage==1 || Stage==4 + FlowIncompleteBatchCount==0                  → "略"
  Stage==1 || Stage==4 + FlowIncompleteBatchCount>0                   → "疑问"
  else                                                                → null
  ```
- **注意：** 主号级聚合意味着同主号下所有工单共享同一个流转性判定结果（除非有 WorkOrderPlan 手工覆盖）

- 计算字段从 Group 1-4 扩展到 Group 1-21（含返整执行/合格流转/有效流转/次品总量/成品入库/实时关注含主号计划性/工单需求调整；过程不合格/成检不合格/汇总不合格三组已随 V6.7 删除，物料执行组已随 V5.7 删除）

### 3.5 ScheduleStage 五档全主号级判定（V2.15）

- 档位：**0 主号暂停 / 1 主号完成 / 2 原料锁定 / 3 生产执行 / 4 成品检验**（`IntStatusDisplayHelper.GetScheduleStageText` 五档中文 + null/fallback）
- 判定优先级（批量全量 `RefreshAllAsync` 与增量 `RefreshByWorkOrderNosAsync` 两路径一致）：
  ```
  IsPaused ? 0
  : MainNoWarehousingStatus >= 2 ? 1        // 主号入库完结/超额 → 主号完成
  : MainNoFlowStatus is 0 or 1 ? 2          // 主号有效流转未满足 → 原料锁定
  : 主号下任一工单有活动批次 ? 3            // 档3/4 主号级上卷
  : 4
  ```
- **档3/4 主号级上卷**：`producingByWo`（工单 → 有活动批次：未产/在产/暂停）→ `producingByMainNo`（主号 → 组内任工单有活动批次）→ 逐 summary 应用。主号级聚合保证同主号下所有工单档位一致
- 字段改名：「关注状态」→ **「主号关注」**（ScheduleStage）、「工单计划性」→ **「主号计划性」**（UrgencyLevel），读模型字段注释、页面列 Label（如「主号-关注」/「主号-计划性」）、Helper 方法 GetScheduleStageText/GetScheduleStageOptions 名称不变

### 3.6 入库状态四档（WoWarehousingStatus / MainNoWarehousingStatus，V2.15）

- 档位：**0 无入库 / 1 入库部分 / 2 入库完结 / 3 入库超额**（定尺按支、非定尺按重）
- 阈值由配置表 `WarehouseThreshold` 驱动：CompleteRatio=0.95（入库完结下限）/ CompleteDeviation=100（数量偏差容差）/ CompleteOverRatio=1.05（超额上限）
- 显示统一走 `IntStatusDisplayHelper.GetWarehousingStatusText` / `GetMainNoWarehousingStatusText`（四档）

### 3.7 到料实投一致性七档（V2.16）

- 档位：**0 一致 / 1 待投 / 2 疑问-到料少投 / 3 疑问-到料超投 / 4 错误-无料已投 / 5 错误-无需投料 / 6 略**（`IntStatusDisplayHelper.GetPlanInputConsistencyText`）
- **容差可配置（V3.0，2026-08-24）**：判定容差 ±3%（上界 1.03 / 下界 0.97，档 5 缺口率阈值同用）由 `ConfigParameter.MaterialPlanTolerance.InputConsistencyTolerance` 键驱动，经 `MaterialPlanToleranceProvider` 静态快照下发——排序表达式 `BuildPlanInputConsistencyExpr` / 筛选 `ApplyComputedFilters` / DTO 计算属性三处读同一快照，改配置表保存即生效（API 启动 + ConfigParameterService 写操作后刷新），未配置回退 `MaterialPlanToleranceDefaults` 常量默认值 0.03
- 判定基准 = 实际已投料量(InputWeight) vs 现可投料总重(TotalAvailableWeight=**到货量口径**：G4~G6 用到货量 PiercingSubInWeight+SemiInWeight+FinishInWeight，下单未到货不视为现可；G7~G10 仍为出库/投料量)：
  ```
  阶段门控（判定顺序最前）：主号关注=生产执行(3)/成品检验(4)/主号完成(1) 已过投料期
    理论缺失总料重(计划7项−现可7项) > 计划投料总重×3% → 5（业务已完成还在投料计划，缺口率>3% 必须修正）
    其余（含缺口≤3% 容差内）                          → 6（降噪不细看）
  原料锁定期(2)/主号暂停(0) 走原五态：
    已投>0 且 现可=0          → 4（计划外投料，最异常）
    已投 > 现可×1.03          → 3（超投）
    已投 < 现可×0.97          → 截止到料日(CutoffArrivalDate) 空或>今天 → 0（料未到位）
                                =今天 → 1（操作时间差，正常）
                                <今天 → 2（料已到位需投未投）
    否则                      → 0（±3% 内 / 双零）
  ```
- **截止到料日 CutoffArrivalDate**（实体字段，迁移 `20260807082102_WorkOrderExecutionSummaryAddCutoffArrivalDate`）= G4~G6 仓库进库（InventoryBatch.SourceOrderNo 经采购/委外来源单号映射回工单）InboundDate 与 G7/G8 出库（OutboundRecord.OutboundDate）的最大值，仅与仓库"到料+出库"相关；主号级 `MainNoCutoffArrivalDate` = 组内 Max（ComputeMainNoInputAggregation 内）

## 5. WorkOrderListSummary 详情

### 5.1 概述

`WorkOrderListSummary` 是**用料计划总览页面**（`/material-plan-overview`）的数据源，存储工单基础信息 + 预计算的用料计划聚合数据。

### 5.2 数据来源（11 张源表）

| 表 | 用途 | 对应 Group |
|------|------|-----------|
| `WorkOrders` | 工单基础信息 | Group A |
| `SalesOrders` | 签订日期、订单号关联 | Group A |
| `CustomerProfiles` | 业务员、最终用户 | Group A |
| `OrderItems` | 规格、交货状态、长度、重量等 | Group A |
| `PurchaseSemiPlans` | 荒管采购计划聚合 | Group B |
| `PurchaseFinishedPlans` | 成品采购计划聚合 | Group B |
| `InventoryPlans` | 库存使用/库料改制计划聚合 | Group B |
| `RoundBarPiercingPlans` | 圆棒穿孔计划聚合 | Group B |
| `ConfigParameters` | 满足率计算配置阈值 | Group B |
| `InProcessReworkPlans` | 在制修检计划聚合 | Group B |

### 5.3 字段构成（约 50 字段）

## 6. QualityProcessTracking 详情

### 6.1 概述

`QualityProcessTracking` 是**质量过程跟踪列表页**的数据源，按 `MaterialReceiveCheckId` 唯一存储。将成检到料、成品检验、库存批次、生产记录（断切）等多源数据预聚合并持久化，支持 DB 级排序和筛选。

### 6.2 数据来源（5 张源表）

| 表 | 用途 |
|------|------|
| `MaterialReceiveChecks` | 成检到料记录（批次信息、接收日期、班次、检验员等 G1 字段） |
| `ProductionBatches` | 批次基础信息（炉号、牌号、规格、生产类型等） |
| `FinalInspections` | 成品检验结果（9 种检验项目的检验日期、合格/不合格汇总） |
| `InventoryBatches` | 入库记录（按批次号关联，计算 G4 入库量/重量/日期） |
| `ProductionRecords`（Cut 工段） | 断切记录（计算 G3 生产断切量） |

### 6.3 字段分组

| 分组 | 内容 | 来源 |
|------|------|------|
| G1 批次信息 | BatchNo, PlantGrade, Specification, WorkOrderNo, SalesOrderNo, SourceUnit, FurnaceNo, 等 20+ 字段 | MaterialReceiveChecks + ProductionBatches 直读 |
| G2 检验日期 | 9 种 InspectionItem 检验日期（PmiDate, DimensionalDate, HydrostaticDate, UnderwaterPressureDate, VisualDate, EndoscopyDate, EddyCurrentDate, UltrasonicDate, PortColoringDate） | FinalInspections 按类型拆分 |
| G3 检验汇总 | ProductionCutQuantity, TotalQuantity, QualifiedQuantity, 不合格分类汇总, MaxInspectionDate | FinalInspections + ProductionRecords 聚合 |
| G4 入库 | InboundQuantity, InboundWeight, InboundDate | InventoryBatches 聚合 |
| G5 状态 | QualityStatus（入库存疑/待检验/检验中/完成检验），异常完成是展示层推导值（IsForceCompleted=true 时强制显示）；**预检（InspectionType=PreInspection）行前端恒显示"略"（V2.17，不参与执行状态跟踪）** | 4 种 DB 存储值根据检验数据完整性 + 入库数据计算，异常完成在打印时由 IsForceCompleted 推导 |

### 6.4 刷新机制

**刷新方法：** `QualityProcessTrackingService.RefreshByMrCheckIdAsync(int mrCheckId)`

与 WorkOrderExecutionSummary 一致的增量触发模式：

| 触发源 | Service | 说明 |
|--------|---------|------|
| MaterialReceiveCheckService | 成检到料 CUD | 直接传 MRCheck.Id |
| FinalInspectionService | 成品检验 CUD | 通过 ProductionBatchId 反查 MRCheck.Id |
| InventoryService | 库存批次 CUD | 通过 ProductionBatchNo 反查 MRCheck.Id |
| ProductionRecordService | 断切记录 CUD | 通过 ProductionBatchId 反查 MRCheck.Id |

> **V2.7 变更**：以上 QualityProcessTracking 刷新调用均已从 `void` fire-and-forget 改为 `async Task` + `await`，确保刷新操作在业务方法返回前完成，不再依赖后台 fire-and-forget。

刷新流程：
```
触发事件 → RefreshByMrCheckIdAsync(mrCheckId)
  → 加载 MRCheck + ProductionBatch 基础信息
  → 加载该批次所有 FinalInspections
  → 加载该批次关联的 InventoryBatches
  → 加载该批次 Cut 工段 ProductionRecords
  → 计算 G1-G5 所有字段
  → Upsert 到 QualityProcessTracking 表
```

### 6.5 与 WorkOrderExecutionSummary 的异同

| 维度 | WorkOrderExecutionSummary | QualityProcessTracking |
|------|--------------------------|----------------------|
| 唯一键 | WorkOrderNo（工单级） | MaterialReceiveCheckId（到料记录级） |
| 行数规模 | ~数百 | ~数千 |
| 刷新粒度 | 工单级 + 兄弟工单 | 单 MRCheck 记录 |
| 族展开 | 无（每工单一行） | 无（每 MRCheck 一行） |
