**上次变更（V2.20）**：`GET api/order/progress` **进度树叶下新增「生产批次名单」+ 生产执行分支口径由快照改实时重算**（**无 EF 迁移 / 无数据变更 / 无权限变更 / 零新端点**；DTO 增 1 字段 + 2 新类）：
- **`MainProgressLeafDto` 新增 `BatchSegments`（`List<LeafBatchSegmentDto>`，空集合 = 不渲染名单）**，新增两个 DTO：**`LeafBatchSegmentDto`**（`Key` 英文段键 / `Label` 中文段名（服务端拼好）/ `WeightKg` 段合计 / `BatchCount` / `Batches`）与 **`LeafBatchItemDto`**（`BatchId` = `ProductionBatch.Id`（供弹窗用）/ `BatchNo` 生产编号 / `WeightKg` 仅供 tooltip 对照，不在行内渲染）。**英文 Key + 服务端拼中文 Label**，前端只做拼接、不做中文判断。
- **生产执行分支（`Production`，Title 仍为 `生产执行[待产]`，标签未改）改为实时重算**——原取 `WorkOrderExecutionSummary.PendingSection*` **快照**，现改由共享计算器 `MES.Services/Helpers/ProductionPendingNodeHelper` 对 `ProductionBatches.Include(ProcessGroups)` **实时**计算（按该订单的各 `WorkOrderNo` 收窄取数，与读模型刷新取数范围严格对齐；按 `ProductionMainNo` 分组，主号级 = 该主号全部工单批次并集一次算完）。**节点 Key / 中文 Label / 叶子顺序与数值口径逐字不变**（8 节点：RoughTubeProcessing 荒管处理 / InProcessRepair 在制修检 / ColdRoll60 / ColdRoll50 / ColdRoll30 / ColdRoll20 / ThreeRollColdRoll / ColdDraw），仍为「重量 > 0 才建叶」。
- **批次名单分段口径**——对每个节点，被计入的批次按 `batchCurrentSeq` vs `targetSeq` 切两段：**`== targetSeq` → 在产 `InProgress`**（批次已在本节点工序组内、目标工段未完成）；**`< targetSeq` → 在途 `InTransit`**（还没做到本节点工序组）。不计入（与今一致）：`> targetSeq`（已越过）/ 该批无此工序组 / 该工序组无目标工段 / `Status ∈ {Completed, InFinalInspection}`。**安全绳不变式：`Σ在产 + Σ在途 == 叶 WeightKg`**（分段只是对同一命中集合分区，不增不减）。**段序固定「在产 → 在途」**（该段有批次才出现）；**段内按 `BatchNo` `StringComparer.Ordinal` 升序**（显式排序，不依赖集合组序）。
- **成品检验分支（`FinalInspection`）名单恒 1 段**——每批恰好落一个档，无「在途」概念：`Key="Batches"`、`Label=` 该档中文阶段名、`WeightKg=` 叶重、`BatchCount = Batches.Count`。**重量与名单必须取自同一行**（沿用 `GroupBy(ProductionBatchId).First()` 去重铁律，`BatchId = first.ProductionBatchId`）；段内同样按 `BatchNo` Ordinal 显式排序。⚠️ `KanbanStageKeys` 是「中文字面量即存储值」的固定四值状态机，**未新建枚举、未往 `EnumDisplayDefinitions` 加条目**。
- **⚠️ 口径分叉（须知晓）**——本分支改为实时后，与「工单执行状况」页的快照（未点「即时更新」时）**可能不一致**；`WorkOrderExecutionSummary.PendingSection*` 仍由同一计算器产出、供工单执行页沿用，两侧**共用一份算法**但**取值时机不同**，会长期分叉。同时 `DeformedProcessCompleted` / `ProductionAttentionProcess` 仍是快照，同一棵树内出现「实时 + 快照」并存。
- **⚠️ 已知取舍（零权重批次）**——`CurrentValidWeight == null` 的批次计入名单但计 0kg；若某节点全是此类批次 → 叶因「重量 > 0」不建 → 名单不可见。属既有显示口径延续，**未改**。

**上次变更（V2.19）**：`GET api/customer/list` **发货区间与接单区间拆分**——新增两个可选查询参数 **`shipDateFrom` / `shipDateTo`**（发货日期区间，`yyyy-MM-dd`，**无迁移 / 无权限变更**；`CustomerProfileDto` 无字段增删）。至此客户往来支持**两个互相独立、可叠加**的区间：
- **接单区间** `signDateFrom` / `signDateTo` → 仅驱动 **`YearOrderCount/Weight/Amount`**（改按 `SalesOrder.SignDate ∈ 区间` 统计；前端表头此时显示「区间接单」）。**不再驱动已发货桶**（V2.18 的单区间双驱动语义已拆开）。
- **发货区间** `shipDateFrom` / `shipDateTo` → 仅驱动 **`ShippedCompleted*` / `ShippedOther*`**（改按 `OutboundRecord.OutboundDate ∈ 区间` 统计；前端表头显示「区间已发货(整单/非整单)」）。
- 未传区间的维度回落**自然年**口径；`TotalOrder*`（累计接单，全时段）与 `StockCompleted*`/`StockOther*`/`WipNone*`/`WipPartial*`（待发货/待在产，**存量口径无日期语义**）**恒保持原语义**。前端在任一区间生效时把「非该区间的列」渲染为「—」以防误导。
- **⚠️ 区间模式下服务端追加行过滤**（`CustomerService.GetPagedInRangeModeAsync`）：任一区间生效时，**先按「激活列有数据」（该列 `Count>0 || Weight>0`）过滤客户行、再分页**，`PagedResult.TotalCount` 返回**过滤后条数**——即「共 N 条记录」与页面实际可见行同口径，防区间口径下满屏空行。未启用区间走原路径（全客户）。**同一端点为两处入口共用**：报表总览「客户往来数据」卡（纯 HTML 表，本地渲染全量）与源列表页「客户管理」`/customers`（`MudTable` 服务端分页）——后者因此天然获得与报表卡一致的过滤行为（客户档案量级小，内存过滤可接受）。统计字段由 `ApplyStats` 从同一份桶回填，`AttachStatsAsync` 复用同一方法保证两路径口径一致。
- **结束日按闭区间含当天**（服务端 `< To.AddDays(1)`）。两区间各自两端皆空 = 该维度沿用原「本年」行为；**全空 = 完全沿用原「累计 + 本年」行为**。⚠️ `QueryParams.SignDateFrom/SignDateTo` 与 `WorkOrderQueryParams` 原同名属性同语义，后者重复声明已删除上提至基类。

**上次变更（V2.18）**：`GET api/customer/list` 新增两个可选查询参数 **`signDateFrom` / `signDateTo`**（接单日期区间，`yyyy-MM-dd`，**无迁移 / 无权限变更**；`CustomerProfileDto` 无字段增删）：任一端有值即进入**接单区间模式**——① 当期接单桶（响应字段 `YearOrderCount/Weight/Amount`）改按 `SalesOrder.SignDate ∈ 区间` 统计（前端表头此时显示「区间接单」）；② 已发货桶（`ShippedCompleted*` / `ShippedOther*`）改按 `OutboundRecord.OutboundDate ∈ 区间` 统计（前端表头显示「区间已发货」）；③ `TotalOrder*`（累计接单）与 `StockCompleted*`/`StockOther*`/`WipNone*`/`WipPartial*`（待发货/待在产，存量口径）**保持原语义不受影响**（前端在区间模式下把「累计接单」列渲染为「—」以防误导）。**结束日按闭区间含当天**（服务端 `< signDateTo.AddDays(1)`）。两端皆空 = 完全沿用原「累计 + 本年」行为。⚠️ `QueryParams.SignDateFrom/SignDateTo` 与 `WorkOrderQueryParams` 原同名属性同语义，后者重复声明已删除上提至基类。

**上次变更（V2.17）**：订单进度树完结主号分支改为「**投料 + 产出**」两维度口径（**无迁移、路径/权限不变**）：① `OrderMainProgressDto.ProductionInput` 重量改取**生产批次工艺卡** `ProductionBatch.InputWeight` Σ（批次仅排除「返整 / 委外生产 / 对外加工」，**不限制造物品**）；② 新增 `OrderMainProgressDto.DefectInbound`（次品库 DEFECT 6 类物料经生产批号反查聚合）；③ `MainProgressLeafDto` 新增 `ReturnWeightKg`（**仅次品入库叶可能非 0**，同叶退货出库量）；④ `SurplusInbound` / `FinishedStockInbound` 标题由「余料入库 / 备料入库」更名「**在制品入库 / 备料成品**」（字段名与口径不变）；⑤ `Warehousing` 标题「成品入库」→「**订单成品入库**」；⑥ **删除** `ProcessInspectionDefect` / `FinalInspectionDefect` 两字段。零值叶省略 / 空分支为 null 规则不变。

**历史变更（V2.16）**：订单进度树完结主号 **成品检分支由 3 叶改为 4 叶**（随成品检不合格品去向 5 档）——成品检 = 入在制库(`FinalInspectionInProcessWarehouseWeight`, 新叶 Key `InProcessWarehouse`) + 可入备库(`FinalInspectionWarehouseWeight`, Key `Inbound`) + 入次品库(`FinalInspectionScrapWeight`, Key `Scrap`) + 退货(`FinalInspectionReturnWeight`, Key `Return`)。过程检分支不变（3 叶）。零值叶省略规则不变。

**历史变更（V2.15）**：订单进度树完结主号 **过程检 / 成品检分支由 2 叶改为 3 叶**——过程检 = 入在制库(`ProcessInspectionWarehouseWeight`) + 入次品库(`ProcessInspectionScrapWeight`) + 退货(`ProcessInspectionReturnWeight`)；成品检 = 可入备库(`FinalInspectionWarehouseWeight`) + 入次品库(`FinalInspectionScrapWeight`) + 退货(`FinalInspectionReturnWeight`)。叶 Key 仍为 `Inbound`/`Scrap`/`Return`，零值叶省略规则不变。

**LeafBatchSegmentDto（五级=叶下名单分段，2026-09-15 新增）**

| 字段 | 类型 | 说明 |
|------|------|------|
| Key | string | 英文段键：生产执行叶 = `InProgress`（在产）/ `InTransit`（在途）；成品检验叶 = `Batches`（单段） |

| 字段 | 类型 | 说明 |

### 5.4 理算重量计算规则

**公式：**
- 理算重量 = 密度 × 3.1416 × 壁厚有效值 × (外径有效值 - 壁厚有效值) × 米数 / 1000


**参数计算：**

| 参数 | 公式 | 说明 |
|------|------|------|
| 壁厚有效值 | 壁厚 - 0.5 × 壁厚负差 + 0.5 × 壁厚正差 | 考虑偏差后的有效壁厚 |
| 外径有效值 | 外径 - 0.5 × 外径负差 + 0.5 × 外径正差 | 考虑偏差后的有效外径 |
| 系数 | 3.1416 | π的近似值 |

**米数计算规则：**

| 长度状态 | 米数来源 | 公式 |
|----------|----------|------|
| Fixed（定尺） | 系统自动计算 | MaxLength × 支数 / 1000 |
| Range（范围尺） | 手工录入 | 用户输入的 Meters |
| NonFixed（非定尺） | 手工录入 | 用户输入的 Meters |

**边界处理：**

| 场景 | 处理规则 |
|------|----------|
| 计算结果为负数 | 设为 0 |
| 米数或支数为空 | 理算重量计算结果为 0 |
| 保留小数位数 | 2位 |

### 5.5 规格生成规则

| 外径 | 壁厚 | 生成的规格 |

| 项目 | 规则 |
|------|------|
| 实现方式 | 使用 RowVersion 字段（SQL Server timestamp） |
| 冲突处理 | 抛出异常，提示用户刷新后重试 |

### 5.12 订单删除时自动清理工单与通知

- 当订单被物理删除时，系统自动执行以下操作：
  1. 物理删除该订单下的所有订单项次和产品要求
  2. 物理删除该订单下的所有工单
  3. 若有工单被清理，生成一条“订单删除通知”（记录订单号、清理工单数量）
- 该通知由工单模块负责展示和处理，订单模块仅负责生成。

## 七、错误码定义

| 错误码 | 说明 | 场景 |
|--------|------|------|
| 200 | 成功 | - |
| 400 | 业务错误 | 订单号已存在、客户不存在、牌号不存在等 |
| 401 | 未认证 | 未提供或提供无效的JWT |
| 403 | 无权限 | 角色权限不足 |
| 404 | 资源不存在 | 订单ID不存在 |
| 409 | 并发冲突 | 乐观并发控制冲突 |
| 500 | 系统错误 | 服务器内部错误 |

### 业务错误示例

| 错误消息 | 说明 |
|----------|------|
| 订单号必须为11位字符 | 订单号格式错误 |
| 订单号已存在 | 创建订单时订单号重复 |
| 客户不存在 | CustomerId无效 |
| 标准牌号无效 | StandardGrade 在牌号对照表中不存在 |
| 定尺时必须填写长度 | Fixed时MinLength为空 |
| 范围尺时必须填写最小长度和最大长度 | Range时MinLength或MaxLength为空 |
| 已取消的订单不能删除 | 尝试删除Cancelled状态的订单 |
| 已取消的订单不能修改 | 尝试修改Cancelled状态的订单 |
| 订单已被其他用户修改，请刷新后重试 | 乐观并发控制冲突 |
