## 二、与商业 MES 的核心差异

### 2.1 商业 MES 的典型构成

商业 MES（西门子 Opcenter、鼎捷、用友等）一般包含：

```
核心层（必备）
  ├─ 订单/工单/批次管理
  ├─ 质量管理
  ├─ 仓库管理
  ├─ 设备管理
  ├─ 报表系统
  └─ 质量实验室（理化检测）

扩展层（加分项）
  ├─ APS 高级排程（有限产能算法 + 甘特图）
  ├─ SCADA/IoT 集成（设备数据自动采集）
  ├─ SPC 统计过程控制（控制图 + Cp/Cpk）
  ├─ 模具/工装寿命管理
  ├─ 计件工资统计
  ├─ 能源管理
  ├─ 多租户/多工厂
  └─ 国际化
```

## 五、工程侧差距（2026-09-15 新增）

> **结论先行**：功能面已经不缺骨架，**短板全在工程侧** —— 上线靠人肉、改动不落库、生产无日志无健康检查。
>
> 2026-09-14 的全站故障就是这套短板的集中兑现：95 个 `.razor` 首行 `@page` 的 `@` 被批量脚本弄丢，**编译 0 错误 0 警告、3529 个单测全过，却一个路由都没注册**，每个页面都落到 `App.razor` 的 `<NotFound>`，全站显示「抱歉，此页面不存在。」。

### 5.1 那次故障暴露了什么

| 本该拦住的防线 | 实际情况 |
|---|---|
| 编译器 | 裸 `page "/orders"` 是合法的 Razor 文本，**0 错误 0 警告** |
| 单元测试 | 3529 个用例全过 —— 没有一条覆盖「路由是否注册」 |
| 部署后冒烟 `06-verify.ps1` | 原 4 项检查（`/` 200 / manifest 200 / login 400 / hangfire 401）**在该次故障中全部通过**：nginx SPA fallback 让 `/` 永远是 200，脚本对「路由全丢」完全失明 |
| 人工检查 | 只能逐个菜单点 162 个页面 —— 这就是当时的发现方式 |

### 5.2 差距清单

| 差距项 | 现状 | 状态 |
|------|------|------|
| **无 CI** | 全仓无 `.github/`、无任何 `*.yml`；3529 个测试靠人手跑 | ❌ 缺失 |
| **部署无门禁** | `09-apply-deploy.ps1` 原先仅 28 行：解包 → 裸覆盖，无包体校验、无备份、无回滚 | ✅ **已补**（§5.3） |
| **无路由断言** | `06-verify.ps1` 只查 HTTP 码，对 09-14 那类故障完全失明 | ✅ **已补**（§5.3） |
| **无健康检查** | 部署后只能 `Get-Service` + 人工点菜单，探活靠感觉 | ✅ **已补**（§5.3） |
| **改动不落库** | 工作区一度堆积 **416 个未提交改动**，而 09-06 以来只有 4 次提交 | ❌ 缺失 |
| **无结构化日志** | `Serilog.AspNetCore` 在 `MES.Api.csproj` 里引了，但**全仓 0 处使用**（死依赖）；日志只有 nssm 把 stdout/stderr 追加到 `C:\mes\logs\api.out.log`，**无切割无滚动** → 生产排障只能靠猜，日志长期增长还会撑盘 | ❌ 缺失 |
| **前端无错误边界** | 全仓 **0 处 `ErrorBoundary`** → Blazor WASM 任一组件抛异常即整页白屏，用户连「出错了」都看不到 | ❌ 缺失 |
| **静态资源版本串靠人记** | `app.css?v=` 必须在改 `app.css` 的同一提交里手动抬串（nginx 对 `/css/` 下发一年 `immutable`），无构建期校验 | ❌ 缺失 |
| **无监控告警** | 无 `/health` 轮询、无异常推送，故障靠用户反馈才知道 | ❌ 缺失 |

### 5.3 本轮已完成的三项（P0）

| 项 | 落点 | 做法 |
|---|---|---|
| **路由门禁** | `09-apply-deploy.ps1`（部署前拦截）+ `06-verify.ps1`（部署后复检） | 编译产物里 `.NET` 用户字符串以 **UTF-16LE** 存于元数据 `#US` 堆，所以直接搜损坏标记 `page "/`（丢了 `@` 的裸指令）。好包 **0 命中**、坏包 95 命中，8 MB 文件约 1 秒。**在动任何文件之前**中止部署 |
| **部署可回滚** | `09-apply-deploy.ps1` | 覆盖前把 `api`/`web` 备份到 `C:\mes\_backup\<时间戳>\` 并写 `ROLLBACK.txt`；包体三件套（`MES.Api.dll` / `index.html` / `_framework\blazor.boot.json`）缺失即中止 |
| **健康检查** | `MES.Api/Health/DatabaseHealthCheck.cs` + `GET /api/health` | 注册 `AddHealthChecks` + DB 连通性探活；端点放在 `/api/` 下以复用 nginx 既有反向代理；匿名可访问（部署脚本在服务刚起、尚无 token 时要能探活），只回报状态与耗时，不暴露连接串 |

> **为什么门禁是「二进制搜标记」而不是「数一下路由」**：Blazor 路由在编译期就固化进程序集，源码级扫描只有在构建机上跑才有意义；部署脚本在服务器上只有编译产物，所以直接在 wasm 里搜「不该出现的裸指令」最省事也最可靠。

## 七、加分项（非必需，仅作备注）

以下功能是商业 MES 的常见卖点，但中小钢管厂实际需求不大，作为技术储备记录：

| 功能 | 投入 | 适用场景 |
|------|------|---------|
| **APS 高级排程** | 算法选型 + 6个月+ 产能数据积累 | 多品种大批量混产时才有明显收益 |
| **SCADA/IoT 集成** | 硬件改造 + 边缘网关 + 时序库 | 设备具备数据接口且自动化程度高时 |
| **SPC 统计过程控制** | 控制图算法 + 规则引擎 | 质检仪器直连或有大量连续检测数据时 |
| **多租户/多工厂** | TenantId 隔离 + 架构调整 | 业务扩展到多厂区时 |
| **国际化** | IStringLocalizer + resx | 有海外工厂或海外客户时 |

## 八、总结

```
当前状态：核心业务链完整，可以支撑工厂日常生产管理
            ↓
已补齐：理化检测 9 模块 / 质量证明书 / 计件工资与六期结算 / 质量巡检 + 不合格反馈 + 扫码质量 / 附件体系
            ↓
真正的短板：工程侧（CI / 部署门禁 / 日志 / 监控）—— 不是功能，是「上线与运维的科学性」
            ↓
加分项：APS/SCADA/SPC/多租户 → 当前不需要追
            ↓
后续方向：
  ① 上线工程化补齐（提交纪律 → 日志 → 错误边界 → CI 门禁）
  ② 物料追溯可视化图谱（数据底座已齐）
  ③ 模具/工装寿命管理
```

**一句话：功能骨架已经完整（含工资结算、质量全链、扫码最后一米），2026-09-14 的全站故障说明下一阶段的重点不在「再加功能」，而在「把上线和运维做扎实」——先让改动可回滚、故障可发现、日志可追溯，再谈物料追溯图谱和模具寿命管理。**
