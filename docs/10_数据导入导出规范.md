# 数据导入导出规范

**版本**：V2.21
**最后更新**：2026-09-03

> 本文件从 `04_开发规范.md` §16 独立拆分而来，内容与之同步维护。

---

数据导入导出服务位于 `MES.Services/DataExchange/`（`DataExchangeService.cs` 门面 + `DataExchangeRegistry.cs` 注册表 + `DataImportService.cs`/`DataExportService.cs`），使用 EPPlus 库操作 Excel。端点权限按数据工具三档角色控制：实体列表/导出/模板/预览=`DataToolView`、导入=`DataToolEdit`、一键修复=`DataToolDelete`（策略尾部均含 Admin 隐式全权）。

## 注册表结构

所有支持导入导出的实体在 `DataExchangeRegistry.Registry` 字典中注册（`DataExchangeService` 通过 `DataExchangeRegistry` 静态类访问），每个实体通过 `EntityDef` 定义：

| EntityDef 参数 | 类型 | 说明 |
|---------------|------|------|
| `displayName` | string | 显示名称（用于导出页签） |
| `sheetName` | string | Excel 工作表名 |
| `type` | Type | 对应实体类（typeof） |
| `batch` | int | 导入批次（仅用于分组，实际顺序由 EntityOrder 控制） |
| `keyColumn` | string? | 业务主键属性名（如 "BatchNo"、"OrderNo"），影响重复检测 |
| `columns` | List\<ColumnDef\> | 列定义列表 |
| `compositeKeyColumns` | string[]? | 复合主键属性名数组（如 StandardGradeMapping 的 StandardGrade/StandardGradeCategory） |

## 实体命名规则（上下文-实体名，V2.16）

**全部 73 个实体 `DisplayName` 统一为「上下文-实体名」**（如 `工单-库存计划`、`扫码-工位管理`），上下文前缀按 `DataExchangeRegistry.ContextOrder` 固定顺序归类：

`订单 → 工单 → 批次 → 质量 → 物料 → 仓库 → 设备 → 标准 → 配置 → 扫码 → 系统`

- **用途**：`DisplayName` 同时用作导出/模板的**文件名主体**（前端 `{DisplayName}_模板.xlsx` / `{DisplayName}_yyyyMMdd.xlsx`）与 Excel 工作表名，统一前缀便于按上下文识别文件
- **上下文解析**：`DataExchangeRegistry.GetContext(displayName)` 取 `-` 前前缀，不在 `ContextOrder` 时归「其他」排最后（不应出现）
- **工位/员工归属**：Workstation（工位）/ Employee（员工）是**扫码报工体系**的基础主数据（扫码先扫工位码绑定上下文、再选操作人），自 V2.16 起归入**扫码**上下文
- **配置表归属**：StandardWorkDay / StandardWorkDayDeliveryState / DailyOutputEstimate / DailyProductionCapacity / SectionParagraphConfig 等 5 张排程/流转配置表归入**配置**上下文；ConfigParameter 全局参数归入**系统**上下文；2026-09-03 补齐注册的工序组定义/冷轧产能·机台数·机台组/枚举·字典显示配置 6 表亦以「配置-xxx」命名归入配置上下文（ProcessKey/GroupKey/复合键定位，冷轧三表实体位于 Scheduling 命名空间但导入导出按配置分组）
- **下拉排序**：`GetEntities()` 按 `ContextOrder` 分组升序返回（组内按 `DisplayName` 升序），前端「选择数据类型」下拉直接消费该顺序；`EntityInfo` 携带 `Context` 字段
- **需求调整归属**：OrderDemandAdjustment 由「订单-需求调整」改归「工单-需求调整」——实体 `MES.Data.Entities.WorkOrder`、主键 `WorkOrderId`（一个工单一条），字段全为工单级调整（催单/分批交货/暂停/强制完成/备注），实体/服务/Controller/前端页面本就在工单上下文，仅 DisplayName 与路由历史遗留带 order；API 同步改 `api/workorder-demand-adjustment`

## 注册完整性（全字段覆盖，2026-08-26）

所有实体**全部可写业务属性均已注册**（经反射扫描比对 `ColumnDef.Property` + `FkTargetProperty` 与实体可写属性确认，仅导航属性与 FK 冗余字段未注册）。已注册字段分为三类：

| 分类 | 说明 | 导入行为 |
|------|------|---------|
| 用户录入字段 | 快照/冗余/配置等普通业务字段 | 可导入（覆盖/新增） |
| 系统回写字段（`isSystem: true`） | 由 Service 计算或写操作同步的字段（如批次成检附加/过程检聚合、计划测算结果密度/单重、设备物化状态、定尺切割匹配标识、理论重量等） | 仅导出，导入跳过（防手工篡改破坏一致性） |
| 系统编码字段（`isSystem: true`） | 系统自动生成的编码（SupplierCode 等） | 仅导出，导入跳过 |

**不注册（有意排除）**：
- 导航属性（如 `ProductionBatch.ProcessGroups`、`SalesOrder.OrderItems`）— 非存储列
- 审计字段（CreatedTime/CreatedBy/UpdatedTime/UpdatedBy）与 RowVersion — 系统维护
- 已被 FK 列覆盖的冗余字段（如 PurchaseOrder.SupplierName 经供应商名称 FK 列解析）— 避免列重复

> 说明：`PipeManufacturingType` 在 OrderItem/WorkOrder 中以「物料名称」表头注册（实体属性名即 `PipeManufacturingType`）；早期版本误写为不存在的 `MaterialName` 属性，导致这两张表导出恒为空、导入被跳过，已修复。

**幽灵列清理（V2.13）**：全量逐列静态校验（`ColumnDef.Property`/`FkTargetProperty` 与实体属性反射比对 + 全实体导出/模板/预览闭环）发现并删除 **5 实体 23 个幽灵列**——注册列指向实体不存在的属性，运行时静默跳过（不崩溃）但导致模板多余列、导出恒空列、必填强制无效字段：

| 实体 | 删除列 | 说明 |
|------|--------|------|
| MaterialReceiveCheck | 制造物品/挂牌号/工单号/订单号/来料单位/炉号/工厂牌号/规格/生产类型（9） | 批次冗余展示列，实体从未实现 |
| FinalInspection | 挂牌号/物料名称/关联工单号/关联订单号/来料单位/炉号/工厂牌号/规格（8） | 同上 |
| InProcessReworkPlan | 批次总支数/批次总重量/现有有效原料支数/现有有效原料重量（4） | 批次汇总展示值，实体无字段；其中前 2 列为**必填幽灵列**（强制用户填无效字段） |
| SubcontractOrder | 来源工单号（1） | 实体无 `SourceWorkOrderNo` |
| SalesOrder | 「客户编码」FK 列（1） | 实体无客户外键 `CustomerId`（仅 CustomerName 快照），FK 解析无处写入 |

## ColumnDef 参数

| ColumnDef 参数 | 类型 | 说明 |
|---------------|------|------|
| `Header` | string | Excel 表头名（中文字段名） |
| `Property` | string? | 实体属性名（null 表示仅用于 FK 解析，不直接写入实体） |
| `Type` | Type? | 数据类型（缺省为 string） |
| `isRequired` | bool | 是否必填（导出模板中标记红色） |
| `isEnum` | bool | 是否为枚举类型（导出时输出中文名，导入时自动解析） |
| `isSystem` | bool | 是否系统管理字段（系统自动编码如 SupplierCode，或系统计算的跟踪字段如 HasInputChange，导入时跳过写入） |
| `valueConverter` | Func\<string, object\>? | 值转换器（主要用于 bool：`v => v == "是"`） |
| `IsFkColumn` | bool | 是否为外键列（导入时 FK 解析用） |
| `FkEntityKey` | string? | 引用的实体 Registry 键名 |
| `FkLookupProperty` | string? | 引用实体的查询属性（如 "CustomerCode"、"OrderNumber"） |
| `FkTargetProperty` | string? | 本实体的 FK 目标属性（如 "CustomerId"、"SalesOrderId"） |
| `FkRequiresJoin` | bool | FK 是否为复合键（仅用于 OrderItem：SalesOrderNo+Sequence → OrderItemId） |

## EntityOrder 依赖顺序

导入顺序必须满足 **父表先于子表** 的依赖关系，当前顺序如下：

```
Warehouse → StandardGradeMapping → CustomerProfile → SupplierProfile
    → FurnaceRegistration → ChemicalComposition → ChemicalValidationRule → Ncr
    → SalesOrder
    → OrderItem → ProductRequirement
    → WorkOrder → OrderDemandAdjustment
    → PurchaseOrder → SubcontractOrder → SubcontractReturnItem → ProductionBatch
    → ProcessGroup → ProductionRecord → SectionOutsource → OutsourceRecovery → MaterialReceiveCheck → ProcessInspection → FinalInspection
    → ChemicalAnalysis → HardnessTest → GrainSizeTest → PittingCorrosionTest → IntergranularCorrosionTest → TensileTest → MetallographicTest → FlatteningTest → FlaringTest
    → PicklingInRecord → PicklingOutRecord → OperationLog → InventoryBatch → OutboundRecord
    → Equipment → RepairOrder → MaintenanceOrder → InspectionRecord
    → InventoryPlan → PurchaseSemiPlan → PurchaseFinishedPlan → RoundBarPiercingPlan → InProcessReworkPlan
    → SemiPlanProcessGroup → InventoryPlanProcessGroup → PiercingPlanProcessGroup → InProcessReworkPlanProcessGroup
    → Workstation → Employee → ConfigParameter
    → StandardRegister → StandardRegisterItem → GradeChemicalComposition → GradePhysicalProperty → StandardInspectionRequirement → FactoryInspectionRequirement → SubStandardQuickView
    → StandardWorkDay → StandardWorkDayDeliveryState → DailyOutputEstimate → DailyProductionCapacity → SectionParagraphConfig
```

**核心规则：** `BuildFkCacheAsync` 在导入前查询数据库中已存在的父表记录。如果父表数据还未入库，FK 解析阶段会抛出异常。因此不可跳序导入。

## KeyColumn 与重复检测

`KeyColumn` 决定了导入时的重复检测行为。导入采用单一「覆盖（含新增）」模式（见下文「导入模式」），无 `strategy` 参数：

| 场景 | GetRowKey 返回值 | 重复检测 | 行为 |
|------|-----------------|---------|------|
| 行带 ID（模板/导出均含 ID 列） | 返回 `__ID__:{id}` | 命中 → 覆盖；未命中 → 报错 | ID 不存在时该行报错，防静默变新增 |
| KeyColumn 有值（无 ID） | 返回业务主键值 | 命中 → 覆盖；未命中 → 新增 | upsert |
| KeyColumn=null + CompositeKeyColumns（无 ID） | 返回组合键值 | 命中 → 覆盖；未命中 → 新增 | upsert |
| KeyColumn=null + 无 CompositeKeyColumns（无 ID） | **返回 null** | **无法检测**→ 总是 INSERT | 如数据库有数据则唯一约束冲突 |

## 唯一约束处理（重要）

当实体满足以下**全部**条件时，必须在 `ImportAsync` 中添加"先删后插"特殊处理：

1. **KeyColumn = null**（无法检测重复）
2. **CompositKeyColumns = null**（同上）
3. **数据库中有唯一约束**（如 `UK_ProcessGroup_Seq`）

**已识别的实体及处理位置**（在导入主循环之前执行）：

| 实体 | 唯一索引 | 清理规则 | 代码特征 |
|------|---------|---------|---------|
| ProcessGroup | UK_ProcessGroup_Seq (ProductionBatchId, SequenceNumber) | 删除关联批次下所有旧工序组 | `if (entityKey == "ProcessGroup")` |
| OrderItem | UK_OrderItem_Sequence_Active (SalesOrderId, Sequence) | 删除关联订单下所有旧项次 | `if (entityKey == "OrderItem")` |
| ProductRequirement | UK_ProductRequirement_OrderItemId (OrderItemId) | 删除关联项次下所有旧技术要求 | `if (entityKey == "ProductRequirement")` |
| SubcontractReturnItem | UK_ReturnItem_Seq (SubcontractOrderId, Sequence) | 删除关联委外单下所有旧明细项 | `if (entityKey == "SubcontractReturnItem")` |
| MaterialReceiveCheck | UK_MaterialReceiveCheck_BatchId (ProductionBatchId) | 删除关联批次下所有旧检验到料记录 | `if (entityKey == "MaterialReceiveCheck")` |

**注意事项：**
- ProcessGroup 按 ProductionBatchId 清理；OrderItem 按 SalesOrderId 清理；SubcontractReturnItem 按 SubcontractOrderId 清理；ProductRequirement 按 OrderItemId 清理
- 清理在 FK 禁用后、主循环插入前执行，使用 `RemoveRange` + 立即 `SaveChangesAsync`
- ProductRequirement 的 FK 需要 `FkRequiresJoin`，使用 `"{SalesOrderNo}|{Sequence}"` 复合键解析 OrderItemId

**添加新实体时的检查清单：**
```
□ 在 Registry 中添加 EntityDef
□ 在 EntityOrder 中按依赖顺序添加
□ 检查 KeyColumn 是否能唯一标识行（有则设置）
□ 如 KeyColumn=null → 检查数据库有无唯一约束
□ 有唯一约束 → 在 ImportAsync 中添加先删后插特殊处理
□ 确认表头与实体属性名正确对应
□ 运行测试确认（Registry_包含所有N个实体 + ExportAsync_所有实体_无数据时不报错）
```

## 导入模式（覆盖含新增）

`ImportAsync(entityKey, fileData, userName)` 采用**单一「覆盖（含新增）」模式**，接口不含策略参数：

| 行情况 | 行为 |
|--------|------|
| 行带 ID 且库中命中该 ID | 覆盖更新该记录 |
| 行带 ID 但库中不存在该 ID | **报错**（该行计入失败，防静默变新增导致重复） |
| 行无 ID、业务键命中（KeyColumn / CompositeKeyColumns） | 覆盖更新已存在记录 |
| 行无 ID、业务键未命中 | 新增插入 |

**注意：** 覆盖模式是 **upsert（更新+插入）**，不是"删全部重建"。唯一约束实体（如 OrderItem / ProductRequirement / SubcontractReturnItem / MaterialReceiveCheck）通过上文的"先删后插"特殊处理避免唯一键冲突。

**覆盖语义（全量覆盖，2026-08-26 明确）：** 覆盖更新是**按整行属性全覆盖**——Excel 中空白单元格会清空对应字段（可空字段置 NULL、string 置空串），非空白单元格整体覆盖原值。因此「导出→修改→导入」时，仅需改动目标单元格即可，**不要清空想保留的字段**；前端已在该行为处给出醒目提示。

**预览行为（2026-08-26 增强）：**
- 「将覆盖 N 行」展开明细（逐行展示 Excel 行号 + 目标记录 ID / 业务键 + 「覆盖更新」徽标 + 说明列），供导入前最后确认；带 ID 的行直接显示 ID 数字（去掉内部 `__ID__:` 前缀），不再暴露内部键格式。说明列区分「按 ID 覆盖」与「按业务键覆盖（无 ID）」（`ImportRowResult.ActionNote` + `HasId`）。
- 「将新增 N 行」展开明细（新增 V2.12）：逐行展示「新增」徽标 + 新增原因说明，明确暴露无 ID 新增的重复风险：
  - 无业务键实体（KeyColumn 与 CompositeKeyColumns 均空，如 ProductionRecord/OutboundRecord/OperationLog 等流水表）→「该实体无业务键，无ID上传将新增记录（重复上传会重复插入）」
  - 有业务键但键值为空 →「无ID且业务键为空，将新增记录」
  - 有业务键但未命中 →「无ID且业务键未命中，将新增记录」

## 上传列解析（按表头名匹配，列顺序无关）

**上传读取列的方式是按表头文本匹配，与列的物理位置无关。** 解析流程（`DataImportService.ParseExcel`）：

- 对 Excel 每一列表头，用 `def.Columns.FirstOrDefault(c => c.Header == header)` **精确匹配**（区分大小写）注册列定义，再按该表头的实际位置读取单元格值
- 因此：
  - **列顺序任意调换** → 值按表头名落入正确字段，不会错位
  - **少列** → 缺失列对应字段**保留原值**（不会清空；注意与"存在但空白单元格=清空"的区别）
  - **多列（不同名）** → 多余列不匹配任何注册列，被忽略
- ⚠️ **表头名称不能改**：改表头（含大小写变化）→ 该列**静默失效**（不报错、不写入），用户易误以为已导入。匹配以模板导出/系统注册的表头为准，因此**推荐用「下载数据/生成模板」作为上传基底**，只改数据不改表头
- ⚠️ **多列的唯一例外**：若新增列表头恰好与已有列**同名**（产生重复表头），实际只读取**第一列**内容，后续同名列被忽略——请避免产生重复表头
- **预览区是上传前的最后检查**：改过表头的列会在「将覆盖/将新增」明细中体现出来，导入前务必确认

## FK 约束处理流程

导入事务的完整生命周期：

```
1. BeginTransactionAsync
2. NOCHECK CONSTRAINT ALL（禁用所有外键约束）
3. 唯一约束实体特殊处理（Delete 旧数据）
4. 逐行 ImportRowAsync（含 FK 值解析）
5. SaveChangesAsync（批量提交到数据库）
6. WITH CHECK CHECK CONSTRAINT ALL（启用并校验外键约束）
7. 校验失败 → Rollback；成功 → Commit
```

**FK 解析失败场景：**
- Excel 中的引用值（如客户编码、工单号）在数据库中不存在 → 该行抛异常（计入 FailedCount）
- 批量保存后约束校验失败（如引用了不存在的数据）→ 整个事务回滚

## 导出行为

- `ExportAsync(entityKey)`：查询全表数据，根据 ColumnDef 构建列，解析 FK 显示值，生成 Excel 文件
- `GenerateTemplateAsync(entityKey)`：生成导入模板（表头 + 1 行示例数据），列与"下载数据"完全一致（含 ID 系统列，ID 留空即新增、填写 ID 即覆盖）
- FK 显示值通过 `BuildFkReverseCacheForExportAsync` 将 FK ID 反查回业务主键值
- 枚举类型导出为中文显示值（通过 `EnumHelper.GetDisplayName`）

## 枚举 / Key 类字段的导入导出转换（英文 Key 存储标准）

自 2026-08-06 起，枚举类字段统一**存储英文**、**导入/导出转中文**（详见 `04_开发规范.md` §4.10「枚举类字段中英标准」）：

- **存储为英文 Key 的字符串字段**（非 `isEnum` 枚举类型，而是在 Excel 中用中文、库中用英文 Key 的字段）：
  - 工序：`ProcessName` / `ProcessGroupName` / `CurrentGroupName` / `NextProcess`（`ProcessKeys`）
  - 工段：`SectionName` / `CurrentSectionName` / `NextSectionName`（`SectionKeys`）
  - 产类：`ProductStatus`（`ProductStatuses`）
  - 责任类型：`LiabilityType`（`LiabilityTypeKeys`，2026-08-05 并入字典表）
- **导入**（`DataImportService.ConvertValue` 特殊分支）：Excel 中文 → 英文 Key，`ProcessKeys.ToKey` / `SectionKeys.ToKey` / `ProductStatuses.ToKey` / `LiabilityTypeKeys.ToKey`；未知值保留原样不报错
- **导出**（`DataExportService`）：英文 Key → 中文，工序走 `IProcessDefinitionService.ToDisplayAsync`，工段走 `ISectionNameDisplayService.ToDisplayAsync`，产类/责任类型走 `DictValueDisplayHelper.GetText(dictKey, value)`（配置表 OverrideMap 优先，Keys 常量类兜底）
- **isEnum=true 的枚举字段**（实体属性为 string、声明枚举类型）：导入自动解析（英文枚举名或中文均可），导出 `EnumHelper.GetDisplayName` 转中文

## 添加新实体的完整步骤

1. **在 Registry 中添加定义**（参照已有同类实体）
2. **在 EntityOrder 中添加**（按依赖顺序）
3. **检查唯一约束**（如 KeyColumn=null 且有唯一索引 → 添加特殊处理）
4. **更新测试**：`Registry_包含所有N个实体` 中的计数（当前 73 个实体）
5. **运行测试验证**：所有 DataExchangeServiceTests 通过
