> 版本：V8.36（2026-09-14）
> **本次变更（V8.36）**：**修复「巡检扫码 / 不合格反馈扫码」提交报「巡检人不能为空 / 反馈人不能为空」（纯后端修复，无数据库 / 迁移变更）** —— ① **根因（C# 重载决议陷阱）**：`ApiResponse<T>` 曾并存 `Ok(T data, string message = "操作成功")` 与 `Ok(string message = "操作成功")` 两个重载，当 `T = string` 时单参调用 `Ok("张三")` 按「所有参数都有实参者优于需补默认参数者」绑定到 **message-only** 版本 → 姓名写进 `Message`、**`Data = null`**，且**编译期零提示**；`ScanQualityController.GetCurrentOperator` 正是单参调用，于是前端 `ScanQuality.razor.cs` 取到 `resp.Data == null`，只读框恒显示「（读取中…）」、`_operatorName` 停留空串，提交时把空身份发给服务端。② **修复 a**：删除 `ApiResponse<T>.Ok(string message)` 歧义重载（原位留警示注释 + 调用约定「需自定义消息请给两个实参」），`ScanQualityController` 调用点改 `ApiResponse<string>.Ok(name, "查询成功")`；`GET api/scan-quality/current-operator` 恢复 `data = 姓名`。③ **修复 b（顺带根治同类隐患）**：`CreateInspectionPatrolRequest.Inspector` / `CreateNonconformingFeedbackRequest.Reporter` **去掉 `[Required]`** —— 该字段在扫码链中由 `ScanQualityService` 以登录账号**覆写**（防篡改契约），但 `[ApiController]` 的模型校验发生在 Controller 实例化与服务层覆写**之前**，故即便前端传空也会先被拦成 400 并返回误导性文案；非空校验**下移至** `InspectionPatrolService.CreateAsync` / `NonconformingFeedbackService.CreateAsync`（`BusinessException`，文案不变，手工录入链路语义与表现不变），使「服务端拥有身份」的契约真正成立。④ **回归测试**：新增 `ApiResponseTests`（3 例锁死「单参 `Ok` 必写 `Data`」）、`ScanQualityControllerTests`（`GetCurrentOperator` 姓名写入 `Data`）、两服务测试各补「身份为空白 → `BusinessException`」守卫用例（防「去掉 `[Required]`」被误读为「完全不校验」）；共 75 例通过。

## 一、概述

本文档定义质量管理模块的详细设计，包括页面设计、业务规则、角色权限。

**核心功能**：
- **炉号登记**：来料炉号信息登记，含化学成分录入 + 工厂牌号化分验证 → 与批次关联
- **工厂牌号化学成分**：工厂牌号标准化学成分参考数据维护（⚠️ 已迁移至生产标准上下文）
- **工厂牌号化分验证规则**：工厂牌号各化学元素上下限验证规则配置，含公式"X×C%"（⚠️ 已迁移至生产标准上下文）
- **过程检验**：工序过程中的质量检验记录（跨批次列表+批量创建+内联编辑+列选择+打印）
- **成检到料**：所有工序完成后料到成品检验处的到料确认（独立质量上下文 Service + MaterialReceiveCheck 实体）
- **成品检验**：成品质量检验记录（9类检验项目+批量创建+批次自动填充）
- **质量过程跟踪**：成检到料→成品检验→成品入库整合读模型，按批次聚合展示全过程质量状态
- **理化检测**：理化性能检测记录，9个独立模块，每模块独立表、独立列表页
  - **化学分析（ChemicalAnalysis）**：光谱分析仪检测数据，含15个化学元素含量
  - **硬度检验（HardnessTest）**：硬度检测记录（硬度模式/硬度值）
  - **晶粒度检验（GrainSizeTest）**：晶粒度评级记录（晶粒度等级/测定方法/观察倍数）
  - **扩口试验（FlaringTest）**：扩口性能试验（芯棒锥度/扩口后外径/扩口率/观察结果）
  - **压扁试验（FlatteningTest）**：压扁性能试验（压扁间隙/观察结果）
  - **晶间腐蚀试验（IntergranularCorrosionTest）**：晶间腐蚀性能试验（敏化温度/敏化时间/腐蚀溶液/弯曲角度/观察倍数/观察结果）
  - **金相检验（MetallographicTest）**：金相组织检验（侵蚀方法/电解电压/电解时间/观察倍数/铁素体含量）
  - **点腐蚀试验（PittingCorrosionTest）**：点腐蚀性能试验（抛光级别/原始重量/腐蚀溶液/腐蚀温度/腐蚀时间/最终重量/腐蚀速率/最大点蚀深度）
  - **室温拉伸试验（TensileTest）**：室温拉伸力学性能（原始标距/断后标距/抗拉强度/规定塑性延伸强度Rp0.2/Rp1.0/断后伸长率）
- **质量证明书**：质量证明书管理（列表+创建+编辑/查看，三步创建向导+检验数据自动填充）
- **不合格品报告（NCR）**：不合格品反馈→处置→原因分析→追责→纠正预防措施验证闭环管理

**设计原则**：
- 质量模块独立实体表（FurnaceRegistration/ProcessInspection）
- 炉号登记支持批量创建 + 化学成分自动验证（PREN = Cr + 3.3×Mo + 16×N）
- 工厂牌号化分验证规则支持公式表达式（如 NbMin = "10×C%"）
- 过程检验完全仿照生产记录模式（跨批次独立列表、批量创建、内联编辑、列选择、方向键导航、打印）
- 过程检验实体独立于生产记录（ProcessInspection 表），非 ProductionRecord 子集
- 成检到料独立 Service（MaterialReceiveCheckService）在质量上下文，独立实体表（MaterialReceiveCheck）
- 物理删除策略
- 过程检验创建/更新/删除时自动触发批次跟踪刷新（纳入批次当前执行状态计算）
- 不合格品报告（NCR）单表5组字段设计（G1反馈→G2处置→G3分析→G4责任人→G5纠正措施），2状态机（处理中→已关闭），自动关闭条件（处置完结+责任人处理完结+验证通过/不适用）
- **批次工单号变更联动同步**：Ncr（不合格品报告）表存储了从 ProductionBatch 冗余的 WorkOrderNo 等字段。当批次工单号变更时，自动同步更新（由 BatchService 直接 SQL 更新）。FinalInspection（成品检验）、MaterialReceiveCheck（成检到料）均已移除批次冗余字段（迁移 FinalInspectionRemoveRedundantBatchFields），数据通过 ProductionBatch 导航属性实时投影，无需同步

**关键差异（相对扫码报工）**

1. **不扫工位/员工码**：现场语义是「**某人在某批次某工序工段上发现问题**」。操作人恒等于登录人，无代报场景，故批次码即唯一前置码，工序/工段由页面下拉确定（而非由工位码决定）。
2. **整改窄口径写入**：整改模式提交走 `POST api/scan-quality/inspection-patrol/{id}/rectify` → `InspectionPatrolService.RectifyAsync`，**只写 验证结果 / 整改人 / 是否闭环**，**刻意不调用 `UpdateAsync`**（后者是明细整组替换，会把第一次巡检的明细清空）；非「涉及整改」的单拒绝回填。对应单测见 `MES.Tests/Services/Quality/InspectionPatrolServiceTests.cs`（`RectifyAsync_只写整改字段_不清空第一次巡检明细`）。
3. **闭环定位排序**：「待整改 = `NeedRectification && !IsClosed`」——**不涉及整改的单本就无需闭环，不占待整改位**（否则每次扫码都会被它挡住而无法新建）。`GetByKeyAsync` 排序 = 待整改优先 → 巡检日期降序 → Id 降序。
4. **写入人恒为登录人**：`ScanQualityService` 在服务端覆写 `Inspector` / `Reporter` / `RectificationOperator`（`ICurrentUser.GetUserName()` → `IEmployeeService.GetByCodeAsync` 取员工姓名，查不到则回退登录名），前端传什么都不影响。

## 三、业务规则

### 3.1 炉号登记规则

- **关联工厂牌号自动填充**：输入登记牌号（RegisteredGrade）后，前端自动查询 StandardGradeMapping（标准牌号 → 工厂牌号），填充到关联工厂牌号（RelatedPlantGrade）
- **化学成分验证**：仅当 RelatedPlantGrade 有值且 ChemicalValidationRule 中存在该工厂牌号的规则时执行
- **15个元素验证**：C/Si/Mn/P/S/Ni/Cr/Mo/Cu/N/Nb/Ti/Fe/Al/W，每个元素有 Min 下限和 Max 上限
- **PREN 自动计算**：PREN = Cr + 3.3×Mo + 16×N，自动计算后回填保存
- **PREN 验证**：计算值必须 ≥ PRENMin（若规则设置了 PRENMin）
- **公式支持**：NbMin/TiMin 等字段支持 "10×C%" 格式，实际阈值 = 系数 × C 含量值
- **验证阶段**：创建页批量提交时后端逐行验证；详情页编辑时单行验证
- **仅验证有值的元素**：元素值为 null 时跳过该元素验证
- **炉号可重复**：允许同一个炉号多次登记（唯一索引已取消）

### 3.2 过程检验规则

- 执行序号 SequenceNumber 由服务端自动解析：ProcessGroupId + SectionName → SequenceNumber（来自工序组中该工段的顺序值）。**强制对齐**：创建/批量创建一旦定位工序组即强制取工段步骤号（忽略前端传入值），Update 复用已加载工序组列表重对齐（仅工段不在工序组时保留原值兜底）
- **工段名称默认"检验"**：新建页面工段名称默认值设置为"检验"
- **检验支数平衡验证**：Quantity = QualifiedQuantity + DefectReworkQuantity + DefectWarehouseQuantity + DefectScrapQuantity（仅 Quantity 有值时校验）
- **让步放行验证**：QualifiedConcessionQuantity ≤ QualifiedQuantity（仅两者均有值时校验）
- **检验重量验证**：Weight 不能大于批次现有效原料重量（CurrentValidWeight），超出时返回 BusinessException
- **执行序号范围验证**：新建记录时，该批次的 SequenceNumber 不得超过"该批次最近有检验记录的日期的最大 SeqNumber + 7"。即取该批次所有 InspectionDate < 当前记录日期(.Date) 的记录中，InspectionDate 最大的一天对应的最大 SequenceNumber + 7 作为上限（上限由配置 SequenceJump.MaxJump 控制，默认7）
- **重复记录校验**：同批次+同工序组+同工段已存在则拒绝
- **来料单位自动填充**：输入 BatchNo 后从批次的 SourceName 自动填充
- **批次跟踪联动**：过程检验创建/更新/删除后自动刷新对应批次的跟踪字段（CurrentExecDate/CurrentGroupName/CurrentSectionName 等）
- **生产记录互斥**："检验"工段已在生产记录中禁用，仅通过过程检验模块管理

### 3.3 成检到料规则

- 详见 批次模块详细设计.md §4.9

### 3.4 成品检验规则

- **检验支数平衡验证**：Quantity = QualifiedQuantity + DefectReworkQuantity + DefectInProcessWarehouseQuantity + DefectScrapQuantity + DefectReturnQuantity + DefectWarehouseQuantity（仅 Quantity 有值时校验；单条 Create/Update 与批量 BatchCreate 三处同口径）
- **让步放行验证**：QualifiedConcessionQuantity ≤ QualifiedQuantity（仅两者均有值时校验）
- **检验重量验证**：Weight 不能大于批次现有效原料重量（CurrentValidWeight），超出时返回 BusinessException
- **重复记录校验**：同检验日期+同批次(ProductionBatchId)+同检验项目(InspectionItem)+同操作人(Operator)已存在则拒绝（FinalInspectionService.cs:924）
- **检验项目联动**：切换检验项目为非尺寸（Dimension）时自动清空 OuterDiameterRange/WallThicknessRange/LengthAllowanceRange；切换为非水压（HydrostaticPressure）和非水下气压（UnderwaterPneumatic）时自动清空 Pressure/HoldTime
- **批次信息自动填充**：输入 BatchNo 后通过 `LookupBatchAsync` 查询 ProductionBatch 自动填充批次信息（制造物品/挂牌号/工单号/订单号/来料单位/炉号/牌号/规格/定尺长度/生产类型等），用于表单展示与校验。**注意：FinalInspection 表已移除批次冗余字段，仅存 BatchNo，批次信息经 ProductionBatch 导航属性实时投影，不冗余存储**
- **成检类型判定**：InspectionType（PreInspection=预检/FormalInspection=终检）——创建请求不传时服务端按「优先终检」自动判定（到料含终检→FormalInspection，否则预检→PreInspection，兜底终检）；传了则以传入值为准，但必须校验「指定的成检类型必须在批次成检到料类型集合内」，防止创建即制造不符（与健康通知口径一致）。内联编辑同样校验，不传保留原值
- **批量创建（BatchCreateAsync，`api/final-inspection/batch`）同口径**：显式 InspectionType 须为合法枚举且∈该批成检到料类型集合，不在集合逐行报「成检到料不含「Y」类型，不能指定」，存在错误整批复回滚；不传按「优先终检」自动判定
- **批量重量自动折算（2026-09-05）**：批量路径重量字段（检验/合格/返整/入库/报废重量）缺省而对应支数有值时，按批次单支重（定尺=ProductUnitWeight，非定尺=TheoreticalUnitWeight）×支数折算补位（与单条 CreateAsync 同口径），防批量漏填重量落 0
- **重量自动回填**：DefectReworkWeight/DefectWarehouseWeight/DefectScrapWeight 前端按单支重×支数（AutoFillWeight）自动回填，仅当重量为空时不覆盖
- **定尺长度校验**：批次 LengthStatus=定尺时 FixedLength 必填；非定尺时 FixedLength 必须为空，改填 NonFixedLengthRange
- **定尺长度归属校验**：按「订单号+主号」维度调用 FixedLengthWorkOrder 定尺长度集合校验（仅终检要求，预检无需）
- **定尺切割长度匹配标识（CutLengthMatchType）**：仅终检（InspectionType=FormalInspection）+ 批次 LengthStatus=Fixed + FixedLength 可解析时计算——长度 ∈ 本工单号定尺长度集合→`FullMatch`（完全匹配），否则长度 ∈ 订单+主号定尺长度集合→`MainNoMatch`（主号匹配），其余→null（不适用）；创建/更新时由 FinalInspectionService 计算，批次编辑（LengthStatus/工单号/订单号/主号变更）经 BatchService 级联调用 RecomputeCutLengthMatchByBatchAsync 重算；显示走 CutLengthMatchHelper（完全匹配/主号匹配/空白），MudChip 绿/橙/默认
- **物理删除策略**
- **InspectionItem 枚举存储**：数据库存储为 nvarchar(20)，页面通过 DisplayHelper.GetInspectionItemText() 显示中文

### 3.5 不合格品报告（NCR）规则

- **状态档（V8.31 起 4 档）**：`Pending`（待处理，历史档）/ `Processing`（处理中，**登记即此档**）/ `Closed`（已关闭）/ `Ignored`（**忽略**，V8.31 新增——「忽略」待处理组即按正常流程登记一张此档报告，该组因 `SourceGroupKey` 排重不再列出）
- **自动关闭条件**：保存时自动检测 — DisposalIsCompleted=true ∧ PersonIsCompleted=true ∧ (VerifyResult=Passed ∨ VerifyResult=NotApplicable)，满足则自动变更为 Closed
- **自动回退**：编辑保存时若关闭条件不再满足，自动从 Closed 回退为 Processing（不禁止状态回退）
- **待处理批次两组（V8.30 重构）**：待处理列表按派生来源拆两组——① **待处理批次（正常提交）** = 不合格反馈单（人工上报，主动）；② **待处理批次（超阈值遗漏）** = 过程检验/成品检验按组判定后产出的遗漏组（被动）。两者**同源一次查询**返回，由 `NcrPendingCheckDto.Bucket`（`NcrPendingBucket`：`NormalSubmitted` / `OverageMissing`）区分，前端渲染两张独立表格与卡片。**主动/被动为纯派生**：待处理侧看 `SourceType`（`NonconformingFeedback` = 主动，其余 = 被动），已建单侧看 `Ncr.NonconformingFeedbackId != null`
- **被动记录判据（V8.34 改记录级，取代 V8.30 的「按组一条」）**：**一条检验记录一条**。「超阈值遗漏」行**逐条检验记录**判定，该条记录不合格合计 = **让步放行支 + 各流向支**，**同时严格大于**绝对支数阈值与占比阈值才产出**一条**待处理：`合计 > NcrThreshold/Count`（默认 5）**且** `合计 ÷ 该条记录检验支数 > NcrThreshold/Percent`（默认 0.10）。**让步放行计入分子但不单独成行**（边界值 5 支 / 恰好 10% 均不触发）。⚠️ **不再有「组合计」概念**——同批次同工序（或同批次同成检类型同检验项目）的多条记录**各自独立判定、各自成行**；单条均不超阈值时该批次该维度**不产生任何待处理行**（真库例：批次 95/Dimension 4 条各 2/2/2/3 支，组合计 9 支 11.1% 原会成组，记录级下**不列出**，用户拍板确认）
- **记录判定维度（V8.34）**：过程检验 = 逐条 `ProcessInspection`（携带 批次 + 工序 + 检验项目）；成品检验 = 逐条 `FinalInspection`（携带 批次 + 成检类型（预检/终检）+ 检验项目）。同维度多条记录由卡片「检验日期」列区分
- **记录定位键与排重（V8.34）**：定位键 `SourceGroupKey` = `{来源类型}|{生产批次Id}|{工序}|{成检类型}|{检验项目}|{检验记录Id}`（不适用段留空，**末尾为记录 Id**），由 `NcrService.BuildGroupKey` 统一生成，**两处共用**（列表行 `GroupKey`、`Ncr.SourceGroupKey`）。被动行排重比对：① 已有 `Ncr.SourceGroupKey` 等于该键（**不看状态**，含 `Ignored`）→ 该条记录不列出；② **存量兼容**——已有 NCR 若为改造前的 **5 段旧键**（`BuildLegacyGroupKey`）→ 该维度**全部检验记录**均不列出；③ 已有主动反馈（过程检验口径比 `(批次, 工序)`、成品检验口径比 `(批次, 检验项目)`）→ 该维度全部被动行不列出。建单时前端把 `GroupKey` 原样回传写入 `Ncr.SourceGroupKey`，该条记录建成后不再重复列出（同维度其它记录不受影响）
- **次品流向（V8.34 记录级）**：`Ncr.FlowDirection` 保留，被动行**自动取该条记录支数最多的流向**（并列时按 返整 > 入在制库 > 可入备库 > 入次品库 > 退货 定序取首），建单页只读带出；主动行（不合格反馈）为 `null`（人工上报不预设流向）
- **待处理行明细展开（V8.30，方案 B）**：被动行前端可展开查看该条记录明细（形如「返整2/报废3/让步6」），数据由 `NcrPendingCheckDto` 的 5 档流向支数 + `ConcessionQuantity` 提供（V8.34 起为**该条记录**的值）
- **忽略「超阈值遗漏」记录（V8.31 改造：登记即忽略，无独立台账；V8.34 起作用于单条记录）**：对「不合格不多、无需开完整 NCR」的记录，质量负责人可在建单页 G1 之后点「**忽略**」（权限 `QualityEdit`），确认后**按正常建单流程**保存一张 状态 = `Ignored` 的 NCR（`CreateNcrRequest.Status = Ignored`，服务层仅接受该值）。① 该条记录因 `Ncr.SourceGroupKey` 命中而**永久**不再出现在待处理列表（排重**不看状态**，无「自动复活」）；② **无独立台账、无恢复入口**——如需撤销，直接编辑/删除那张 NCR；③ 列表页无「显示已忽略」开关；「忽略」状态在列表中以 `Color.Dark` 展示中文「忽略」
- **G1 问题反馈字段（V8.30；V8.34 起取值改记录级）**：被动行比主动行**多 4 个字段**，顺序固定为 `… 次品支数 / 次品重量 / 问题描述 / 次品流向 / 让步支数 / 让步重量 / 让步说明`。其中：**次品支数** = 该条记录各流向支数合计（**不含让步放行**，与让步放行是两个并列维度）；**次品流向** 只读（见上条）；**让步支数 / 让步说明** 由该条检验记录带出（说明取该条记录的 `ConcessionRemark`，**不再跨记录拼接**），**让步重量** 检验记录无数据源、由质量负责人手填。主动来源（不合格反馈）无让步放行概念，4 个字段整体不渲染、保存时置空
- **来源照片入口（V8.34）**：建单/编辑页「生产编号」右侧 `PhotoLibrary` 按钮，**仅来源记录确有照片时渲染**（`GetSourcePhotosAsync` 返回非空；未拍照/未上传则忽略）；弹窗只读、点击缩略图放大；被动来源按**检验记录 Id** 取该条记录照片（一对一），主动来源按 `feedbackId`；端点 `GET api/ncr/source-photos`（`QualityView`）
- **「反馈部门」= 位置（V8.30）**：过程检验 → **工段**（`ProcessInspection.SectionName`，经 `SectionDisplayHelper.GetSectionNameText`）；不合格反馈（生产工段/过程检验来源）→ **工段**（`NonconformingFeedback.SectionName`）；成品检验 → **成检项目**（`FinalInspection.InspectionItem`，经 `DisplayHelper.GetInspectionItemText`）
- **不合格反馈来源（V8.23）**：`GetPendingChecksAsync` 第三段追加「未生成 Ncr 的反馈单」——判据 `!Ncrs.Any(n => n.NonconformingFeedbackId == f.Id)`，**不受 NcrThreshold 约束**，各 1 行、**`FlowDirection=null`**（V8.28；原 `DisposalMethod=null`）、`SourceType=NonconformingFeedback`（`NcrPendingSourceType` 枚举）、`Bucket=NormalSubmitted`；**列在检验来源组合去重之后**（否则组合键可能被误删）。在 NCR 建单页经查询参数 `feedbackId` 回填 `Ncr.NonconformingFeedbackId`，即视为「已处理」
- **阈值配置项（V8.30 收敛；V8.34 起判定单位为单条记录）**：`NcrThreshold` 由原 8 项（ReworkCount/ReworkPercent/WarehouseCount/WarehousePercent/ScrapCount/ScrapPercent/ReturnCount/ReturnPercent）**收敛为 2 项** —— `Count`（**单条记录**不合格合计触发绝对支数，严格大于，默认 5）与 `Percent`（触发占比，严格大于，默认 0.10 = 10%）。旧 8 项在迁移中删除
- **批次信息冗余**：WorkOrderNo/PlantGrade/Specification 从 ProductionBatch 冗余，创建时通过 LookupBatchAsync 自动填充
- **SourceInspectionItem**：存储来源检验项目名称，用于卡片排重和自动填充
- **物理删除策略**

### 3.6 不合格反馈单规则（V8.14，V8.29 增来源类型三分支）

- **定位**：只登记问题，不做处置。与「不合格报告（NCR）」是两个独立子菜单——本单不含处置方式/责任分析/纠正措施等字段，**也不带任何处理状态**；**「已处理」= 该反馈单是否已生成 Ncr**（`Ncr.NonconformingFeedbackId` 外键，`SET NULL`）。未生成 Ncr 的反馈单进入「不合格报告」页的「待处理批次」（不受阈值约束），建单即闭环
- **来源类型 `SourceType`（V8.29，必填）**：枚举 `NonconformingFeedbackSourceType`——**生产工段 ProductionSection**（正式生产前由生产工段填报）/ **过程检验 ProcessInspection** / **成品检验 FinalInspection**。**来源决定位置信息口径**，是「位置字段随来源自适应」的唯一开关
- **位置信息分档（V8.29）**：生产工段 / 过程检验 → **工序 + 制造规格 + 工段**（原口径不变，工段必填、执行序号随工序组对齐）；成品检验 → **工序 + 检验项目**（**无工段概念**，`SectionName`/`SequenceNumber` 落库为 NULL，`InspectionItem` 必填）。服务层 `NormalizeLocation` 强制归一：**越档的字段一律清空**（成品检验带工段会被清掉，反向亦同）
- **预检/终检由推导得出，非用户输入（V8.29）**：**不做「预检/终检」下拉、也不落库**；由「工序 + 该批次是否含附加成检工序组」推导 —— ① 工序 = 附加成检 → **终检**；② 批次含附加成检、工序 ≠ 附加成检 → **预检**；③ 批次不含附加成检 → **全部终检**。前端只读展示，推导依据由 `LookupBatchAsync` 的 `HasAdditionalFinalInspection` 提供
- **记录模式对齐生产记录**：批次冗余（`ProductionBatchId`/`BatchNo`/`WorkOrderNo`/`PlantGrade`）+ 工序组（`ProcessGroupId`/`ProcessName`/`ManufacturingSpec`）+ 位置（`SourceType` + `SectionName`/`SequenceNumber` 或 `InspectionItem`）+ 数量
- **生产编号必填且必须存在**：创建/更新时按 `BatchNo` 查 `ProductionBatch`，不存在抛 `BusinessException("生产编号不存在：X")`
- **冗余字段由服务端回填**：`WorkOrderNo`/`PlantGrade` 一律取自批次（忽略前端传值），防手改漂移
- **工序组解析**：`ProcessGroupId` 优先用传入值；传 0/空则按「工序名称 + 制造规格」在*该批次的工序组*中匹配，匹配不到为 0
- **执行序号对齐**：定位到工序组后取 `GetSectionSequence(SectionName)`（工段步骤号）作为 `SequenceNumber`；工段不在工序组时保留前端传入值兜底；**成品检验档（无工段）恒为 NULL**
- **产类自动计算**：`ProductStatusHelper.Calculate(ProcessName, ManufacturingSpec, batch.ManufacturingItem, processGroups, batch.Specification)`，前端只读，不接受手填
- **不合格重量**：`ComputeDefectWeight` —— 手填值优先；留空且 来料重量/来料支数/不合格支数 三者齐全且支数 > 0 时按 `来料重量 ÷ 来料支数 × 不合格支数` **四舍五入取整**（`MidpointRounding.AwayFromZero`）；否则为 null
- **数据来源 DataSource**：默认 `MANUAL`（手动录入）；预留 `SCAN`（扫码报工带出，本期未接入）
- **附件上限**：单反馈单最多 **4 张**（`MaxAttachmentCount` = `QualityPhotoLimits.PerRecord`，前后端常量需一致，V8.27）；超限抛 `BusinessException("附件数量已达上限（4 张）")`
- **附件真实存储**：文件本体落 `Attachment:RootPath`（缺省 `AppContext.BaseDirectory/attachments`），存储名为服务端生成的 `GUID + 小写扩展名`；DB 只存 FileName/StoredName/ContentType/SizeBytes/SortOrder
- **附件安全**：①扩展名白名单（jpg/jpeg/png/webp/gif/bmp）；②单文件大小上限（默认 5 MB，配置可调），流式写入后二次复查，超限即删文件；③`ResolveSafePath` 归一化校验拒 `..`/路径分隔符/越出根目录，防目录遍历
- **删除联动**：删除反馈单时先逐张删磁盘文件（失败仅告警不阻断），再删主记录（附件行级联删除）；删除单张附件先删 DB 行再删磁盘
- **筛选上下文缓存**：`CacheKeys.NonconformingFeedbackFilterContexts`（MemoryCache），创建/更新/删除后 `Remove` 失效
- **物理删除策略**：物理删除，ConfirmDialog 确认

### 3.12 巡检单规则（V8.17）

- **定位**：质量检验的**一种类型**（过程巡检记录），**独立建表**（`InspectionPatrol`），不复用过程检验/成品检验等既有表；菜单为质量管理首项，**不新增角色**（复用 QualityView/Edit/Delete）
- **记录模式对齐生产记录/不合格反馈**：批次冗余（`ProductionBatchId`/`BatchNo`/`WorkOrderNo`/`PlantGrade`）+ 工序组（`ProcessGroupId`/`ProcessName`/`ManufacturingSpec`/`SectionName`/`SequenceNumber`）+ 产类
- **存储口径**：除 `NeedRectification` 为 bool 外**其余字段全部文本**（含 在产单位/车间、在产设备名、在产操作人、巡检项、巡检结果、整改内容描述、验证结果）；在产单位/车间虽为文本但前端给**委外单位档案候选**（`position-options` 端点）且允许手输；**巡检人与在产操作人走员工档案单选**（`api/employee/list` 全量启用员工 + 内存模糊过滤，存档写姓名）；**在产设备名为纯手输文本框（无候选）**
- **在产三项与委外联动（V8.18）**：批次带出 `CurrentOutsource` → 在产单位/车间、`CurrentEquipmentName` → 在产设备名；**在产单位命中委外单位档案**时前端置灰并清空「在产设备名/在产操作人」（委外单位无本厂设备与操作人），改回非委外值即恢复；编辑已存单只置灰不清值。**存储层不做委外标记字段**，判定完全在前端展示层，存档仍为纯文本
- **巡检结果自由文本**：方案 α——巡检结果不做结构化/枚举化，**不参与任何聚合统计**
- **生产编号必填且必须存在**：创建/更新时按 `BatchNo` 查 `ProductionBatch`，不存在抛 `BusinessException("生产编号不存在：X")`
- **冗余字段由服务端回填**：`WorkOrderNo`/`PlantGrade` 一律取自批次（忽略前端传值），防手改漂移
- **工序组解析**：`ProcessGroupId` 优先用传入值；传 0/空则按「工序名称 + 制造规格」在*该批次的工序组*中匹配，匹配不到为 0
- **执行序号对齐**：定位到工序组后取 `GetSectionSequence(SectionName)`（工段步骤号）作为 `SequenceNumber`；工段不在工序组时保留前端传入值兜底
- **产类自动计算**：`ProductStatusHelper.Calculate(...)`，前端只读，不接受手填
- **巡检明细一对多且至少一条**：明细存 `InspectionPatrolItem` 子表（`ItemName`/`Result`/`Remark`/`SortOrder`）；服务端 `BuildItems` **跳过巡检项为空的行**，若整组下来 0 条则抛 `BusinessException("请至少填写一条巡检明细")`；**更新为整组替换**（先 `RemoveRange` 旧明细再插新明细）
- **整改块条件化**：`NeedRectification=false` 时服务端**强制清空** `RectificationDescription`/`VerificationResult` 且 `IsClosed` 强制 false（前端亦隐藏整块 + 不提交整改验证照片）
- **数据来源 DataSource**：默认 `MANUAL`（手动录入）；预留 `SCAN`（扫码报工带出，本期未接入）
- **附件按类型分列**：`PhotoType` ∈ {`Patrol` 巡检照片, `Rectification` 整改验证照片}，**每类各最多 4 张**（`InspectionPatrolPhotoTypes.MaxPerType`，前后端常量须一致，V8.27；两类合计单个巡检单最多 8 张）；类型非法抛 `BusinessException("照片类型无效：X")`；超限抛 `BusinessException("{类型中文}数量已达上限（4 张）")`
- **附件真实存储**：文件本体落 `Attachment:RootPath`（缺省 `AppContext.BaseDirectory/attachments`），存储名为服务端生成的 `GUID + 小写扩展名`；DB 只存 PhotoType/FileName/StoredName/ContentType/SizeBytes/SortOrder；安全策略（扩展名白名单 / 大小上限 / `ResolveSafePath` 防目录遍历）由既有 `IAttachmentStorage` 统一保证
- **删除联动**：删除巡检单时先逐张删磁盘文件（失败仅告警不阻断），再删主记录（明细与附件行级联删除）；删除单张附件先删 DB 行再删磁盘
- **闭环快捷切换**：`SetClosedAsync(id, isClosed)` 仅改 `IsClosed` 标记，**不校验是否涉及整改**（列表页仅在 `NeedRectification` 行显示该按钮）
- **筛选上下文缓存**：`CacheKeys.InspectionPatrolFilterContexts`（MemoryCache），创建/更新/删除后 `Remove` 失效
- **物理删除策略**：物理删除，ConfirmDialog 确认

### 3.13 检验记录照片与单据式打印规则（V8.27，照片页版式 V8.26）

- **张数上限单一出口（V8.27 上调）**：过程检验 / 成品检验 / 不合格反馈每条记录最多 **4 张**（`MES.Core.Constants.QualityPhotoLimits.PerRecord`），巡检单**每类各最多 4 张**（`QualityPhotoLimits.PerType` = `InspectionPatrolPhotoTypes.MaxPerType`，两类合计单个巡检单最多 8 张），**前端 MaxCount 与服务端硬校验共用同一常量**；超限抛 `BusinessException`（不静默截断）。⚠️ 前端 `ScanPhotoPicker.MaxCount` 默认值即 `QualityPhotoLimits.PerRecord`；⬆️ **上传张数与打印照片页「每页 2 张」配套**：4 张 = 1 页字段页 + 2 页照片
- **附件真实存储**：与巡检单/不合格反馈同款——文件本体落 `Attachment:RootPath`，存储名为服务端 `GUID + 小写扩展名`；DB 只存 FileName/StoredName/ContentType/SizeBytes/SortOrder；扩展名白名单 / 大小上限 / `ResolveSafePath` 防目录遍历由 `IAttachmentStorage` 统一保证
- **删除联动**：删单张附件先删磁盘再删 DB 行；删主记录时连同全部照片文件一并清理（删盘失败仅告警不阻断主记录删除）
- **落库失败回收**：附件行 `SaveChanges` 失败时必须回收已写盘文件并**清除被跟踪实体**（否则下次 `SaveChanges` 会重试插入产生幽灵附件）
- **扫码直拍不阻断提交**：记录已随主表单落库，照片为提交后逐张补写；单张失败仅计数、最终汇总 Snackbar 提示，**不回滚主记录**
- **单据式打印条数上限**：前端单次最多 **20 条**（每条一页且含照片，避免一次生成过厚 PDF）；服务端不限但 ids 为空/全部不存在均抛 `BusinessException`
- **打印保序**：SQL `IN` 查询不保序，服务端必须按入参 `ids` 顺序重排后再渲染（`orderMap`）
- **照片读取容错**：逐张 `ReadAsync` 时文件缺失/异常**跳过该张**，不阻断整份 PDF 生成
- **NCR 打印照片来源**：仅取**关联不合格反馈单**（`NonconformingFeedbackId`）的附件；未关联反馈或反馈无照片时整区省略（NCR 本体不存照片）
- **照片页恒为第 2 页（V8.25）**：字段区渲染完毕（含审计行）后立即 `PageBreak`，照片独立成页并带归属行；**页数口径（V8.27）** = **无照片 1 页 / 有照片 1 页字段页 + ⌈N/2⌉ 页照片**（单列每页 2 张）——满张 4 张照片 = 3 页、巡检满载 8 张 = 5 页、过程检验两条记录各 4 张 = 6 页。回归保护见 `MES.Tests/Services/Printing/*PrintHelperTests.cs`（字节扫描 `/Type /Page` 断言页数，用例按 `QualityPhotoLimits` 常量取上限）
- **照片尺寸只由高度决定（V8.26）**：`Image(...).FitArea()` 为「等比缩放到『页宽 × ImageBoxHeight』框内」，竖拍/横拍照片均受高度约束（除非照片宽高比大于框宽高比），故**单列铺排不放大照片**；放大照片的唯一手段是加大高度，而高度上限由每页张数决定（每页 n 张时 `h ≤ (709 − 归属行 − 组标题行)/n − 27`）。V8.26 由「每行 2 张 / 200pt（巡检 120pt）」改为「单列每页 2 张 / 290pt」，单张尺寸 +45%（巡检 +142%）

## 五、与其它上下文的集成

### 5.1 批次上下文

- 过程检验（ProcessInspection）关联 ProductionBatch + ProcessGroup，批次号/工序名称/制造规格从批次冗余
- 过程检验创建/更新/删除时通过 `IProductionRecordService.RefreshBatchTrackingFieldsAsync()` 触发批次跟踪刷新
- 批次跟踪计算纳入过程检验记录的最大 SequenceNumber（三路比较：生产记录/工段委外/过程检验）

### 5.2 物料/标准上下文

- 炉号登记的 RegisteredGrade → RelatedPlantGrade 查询 StandardGradeMapping（标准牌号对照）
- 化学成分验证规则（ChemicalValidationRule）以工厂牌号 PlantGrade 为唯一标识
- 工厂牌号化学成分（ChemicalComposition）以工厂牌号 PlantGrade 为唯一标识

### 5.3 成检到料

- 后端独立实现在质量上下文（MaterialReceiveCheck 实体 + MaterialReceiveCheckService）
- 通过 IMaterialReceiveCheckService 接口在质量上下文内管理
