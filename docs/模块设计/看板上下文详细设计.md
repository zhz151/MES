# 看板上下文（Dashboard）详细设计

> 版本：V3.7
> 最后更新：2026-08-21

## 1. 概述

看板上下文是纯查询聚合层，**不创建新表**，从多个现有上下文读取数据并在首页聚合展示。

### 核心原则

| 原则 | 说明 |
|------|------|
| **不建新表** | 看板没有自己的 Entity/DbSet |
| **纯只读** | 看板页面没有任何新增/编辑/删除操作 |
| **首页即看板** | 登录首页（Index.razor）是唯一的看板页面，3 张卡片布局（左列竖排 2 卡各 1/4、右列 1 卡 1/2） |
| **链接到功能页** | 每张卡片点击后跳转到已有的功能页面（非独立看板子页面） |
| **无中间层** | 直接在 Index.razor.cs 中调用各业务 Service，无 DashboardService 中间层 |

### 定位

> **首页回答管理层核心问题："今天工厂怎么样？"**
>
> 点击卡片 → 进入对应功能页查看明细，无需在 Dashboard 上下文中重建。

### 与 V2.7 变更说明

V2.7 曾规划 DashboardService 中间层（注入 7 个 Service + AppDbContext），但实际实现采用**更简化**的方式：
- **未创建** DashboardService（Core/Services/API 均无）
- **未创建** Dashboard DTO 目录（DashboardIndexDto/DashboardUrgencyDto 等均不存在）
- Index.razor.cs 直接注入 4 个业务 Service：WorkOrderExecutionService / SectionParagraphFlowAnalysisService / FinalInspectionPlanService / NcrService
- 无定时自动刷新（30秒 Timer 未实现），手动刷新或切换页面重新加载

- 左列 `MudItem xs="12" md="6" Class="d-flex flex-column"` 内竖排两张 MudPaper：卡片 1（`flex-grow-1 mb-3` + `Style="height:50%"`）、卡片 3（`flex-grow-1` + `Style="height:50%"`），各占页面 1/4

### 卡片 1：工单执行

| 项目 | 说明 |
|------|------|
| 数据源 | `WorkOrderExecutionService.GetDashboardSummaryAsync()` |
| 数据结构 | 3 行（原料锁定 / 生产在产 / 成品检验），2 列（合计、急单合计） |
| 合计列 | 该阶段下所有工单的工单数/总重量（吨） |
| 急单合计列 | 红色 Error Chip 高亮（`MudChip Color="Error"`），仅统计 A+急 + A急（英文 Key `APlusUrgent`/`AUrgent`，经 `UrgencyLevelKeys.IsUrgent` 判定）的工单数/重量（吨） |
| 底部合计行 | 3 阶段汇总 |
| 行点击 | 每个阶段名渲染为**深蓝底 `#0d47a1` + 白字**圆角标签块（`background-color:#0d47a1; color:#ffffff; padding:3px 10px; border-radius:4px`），点击跳转对应页面：原料锁定→/raw-material-lock-plan，生产在产→/batch-plans，成品检验→/final-inspection-plan |
| 负荷总量按钮 | 跳转到 `/plan-overview`（订单负荷总量） |

**BuildCrossTable 逻辑：**
1. 调用 `GetDashboardSummaryAsync()` 获取 `List<WorkOrderExecutionDashboardItem>`（含 ScheduleStage/UrgencyLevel/OrderCount/TotalWeight）
2. 按 ScheduleStage 分组（1=原料锁定/2=生产在产/3=成品检验）
3. 每组内：合计 = SUM(OrderCount)/SUM(TotalWeight)，急单 = SUM 条件为 `UrgencyLevelKeys.IsUrgent(x.UrgencyLevel)`（`APlusUrgent`/`AUrgent`）
4. 重量格式化为吨，**去除小数位、按 4 舍 5 入**（`Math.Round(weight/1000m, 0, MidpointRounding.AwayFromZero)`，避免默认银行家舍入）

> ⚠️ **看板档位是独立三档，非 5 档 ScheduleStage 直接映射**：`GetDashboardSummaryAsync` 内部自行构建 1/2/3 三档——
> - **Stage 1 原料锁定**：取 `WorkOrderExecutionSummary.ScheduleStage == 2`（5 档「原料锁定」）且 UrgencyLevel 非空的行，按「待投料量」（`(TotalWeight - PendingOutsourceFinishWeight) × RawMaterialRatio - InputWeight`）分组
> - **Stage 2 生产在产**：在产批次（Status=未开始/在产）`CurrentValidWeight` 按紧急程度分组（WorkOrderPlan.UrgencyLevel 优先，回退 Summary）
> - **Stage 3 成品检验**：**对齐成检计划看板前 3 档（待到料+待检验+检验中，不含第 4 档「完成检验待入库」）**——复用 `FinalInspectionPlanService.GetKanbanAsync`（候选=InFinalInspection 批次、行=批次+成检类型、强制完成跳过、已入库脱离），筛除完成检验待入库后按批次去重聚合；重量口径=ProductionWeight（生产重量），与成检计划看板完全同源（V3.6 起；旧实现按「有到料未入库」反推，不含待到料、含完成检验待入库、不限批次状态，已废弃）
> 故文中「1/2/3」是看板自身档位编号，勿与读模型 5 档（0主号暂停/1主号完成/2原料锁定/3生产执行/4成品检验）混淆。

### 卡片 2：批次生产（段落流转分析）

| 项目 | 说明 |
|------|------|
| 数据源 | `SectionParagraphFlowAnalysisService.GetAnalysisAsync()` |
| 同源 | 完全采用「批次计划」页中的「段落流转分析」折叠查询列表（`SectionParagraphFlowAnalysisDto`），数据同源、列一致，无首页自拼合并逻辑 |
| 列头 | 生产段落 / 待在产重量(吨) / 总况判定 / 计划重点批流转量(吨) / 计划流转判定 / 特急批重量(吨) |
| 列排序 | 支持点击表头切换升降序（Category→DisplayOrder 为默认序，其余按各数值/字符串） |
| 汇总行 | 待在产重量(吨)合计 + 计划重点批流转量(吨)合计 + 特急批重量(吨)合计 |
| 详情按钮 | 跳转到 `/batch-plans`（批次计划） |

**ApplyFlowSort 逻辑：**
1. 从 API 获取全量段落流转分析项（`ParagraphFlowSvc.GetAnalysisAsync()`）
2. 前端按当前排序列排序 → `_paragraphFlowItems` 渲染
3. 页脚三合计：待在产重量(吨) / 计划重点批流转量(吨) / 特急批重量(吨)（`ComputeFlowFooter`，吨位 4 舍 5 入）

### 卡片 3：质量检验

| 项目 | 说明 |
|------|------|
| 数据源 | `FinalInspectionPlanService.GetKanbanAsync()` + `NcrService.GetPendingChecksAsync()` + `NcrService.GetAllAsync()` |
| 成品检验 | 3 列：（待到料 / 待检验 / 检验中），每列显示总数（X批/Y吨）和紧急数（X批/Y吨） |
| 紧急定义 | `UrgencyLevelKeys.IsUrgent(x.UrgencyLevel)`（英文 Key `APlusUrgent`/`AUrgent`，即 A+急/A急） |
| 成检计划链接 | 与"成品检验"标签同行右侧 |
| 不合格报告 | 2 列：待处理批次（待处理批次数）/ 处理中（Status=Pending/Processing 的 NCR 总数） |
| NCR 列表链接 | 与"不合格报告"标签同行右侧 |
| 详情按钮 | 成检计划→`/final-inspection-plan`，NCR列表→`/quality/ncr` |

**LoadCard3Async 逻辑：**
1. 成品检验：调用 `GetKanbanAsync()` 获取全量计划数据 → 按 KanbanStage 分组（待到料/待检验/检验中）
2. 每组统计 Count + CurrentValidWeight/1000(吨)
3. 紧急统计：额外筛选 `UrgencyLevelKeys.IsUrgent(x.UrgencyLevel)`（`APlusUrgent`/`AUrgent`）
4. 待处理批次：调用 `GetPendingChecksAsync()` 获取待处理批次数
5. 处理中：调用 `GetAllAsync()` filter Status in ("Pending","Processing") 取 TotalCount

## 3. 数据源依赖汇总

| 卡片 | 数据 | 来源 Service | 目标页面 |
|------|------|-------------|---------|
| 1 | 各阶段工单数/重量/急单数 | WorkOrderExecutionService | /plan-overview |
| 2 | 段落流转量分析列表 | SectionParagraphFlowAnalysisService | /batch-plans |
| 3 | 成检计划三阶段统计 | FinalInspectionPlanService | /final-inspection-plan |
| 3 | 不合格(NCR)待处理/处理中 | NcrService | /quality/ncr |

## 4. 哪些页面不需要

以下看板子页面**不需要建立**，因为已有功能页面可以直接链接：

| 原计划子页面 | 原因 | 替代链接 |
|-------------|------|---------|
| 交期预警看板 | 已有排程计划页面（SchedulingPlans），含完整的交期筛选和排序 | `/scheduling-plans` |
| 日产量看板 | 大屏场景需要时可考虑，但先不做 | `/batch-plans`（批次维度看产量） |
| 工段负荷看板 | 已有 SectionProductionStatus 页面 | `/section-production-status` |
| 合格率看板 | 已有不合格报告页面 | `/quality/ncr` |
| 设备状态看板 | 已有维修工单列表 | `/repair-orders` |

### 大屏场景（暂不实现）

如果未来有车间大屏需求，可直接全屏打开功能页面（F11），或新增独立大屏页面挂在大屏专用主机上，不走 Index 看板。

## 5. 目录结构

```
MES.Blazor
  ├─ Pages
  │    ├─ Index.razor                   ← 首页（3 卡片布局：左列竖排 2 卡各 1/4、右列 1 卡 1/2）
  │    └─ Index.razor.cs                ← 直接注入 4 个 Service，无中间层
  └─ Services                           ← 直接使用各业务 Service
       ├─ WorkOrderExecutionService.cs
       ├─ SectionParagraphFlowAnalysisService.cs
       ├─ FinalInspectionPlanService.cs
       └─ NcrService.cs
```

## 6. 依赖的实体

所有数据均来自现有上下文，Dashboard 不需要新增 Entity。

### 引用到的外部 Service

| Service | 所属上下文 | 用途 |
|---------|-----------|------|
| WorkOrderExecutionService | 工单 | 工单执行阶段汇总 |
| SectionParagraphFlowAnalysisService | 计划排程 | 生产段落流转量分析（卡片 2） |
| FinalInspectionPlanService | 计划排程 | 成检计划三阶段（卡片 1 档 3 + 卡片 3） |
| NcrService | 质量 | NCR 处理统计 |
