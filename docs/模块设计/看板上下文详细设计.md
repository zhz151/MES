# 看板上下文（Dashboard）详细设计

> 版本：v3.1
> 最后更新：2026-06-18

## 1. 概述

看板上下文是纯查询聚合层，**不创建新表**，从多个现有上下文读取数据并在首页聚合展示。

### 核心原则

| 原则 | 说明 |
|------|------|
| **不建新表** | 看板没有自己的 Entity/DbSet |
| **纯只读** | 看板页面没有任何新增/编辑/删除操作 |
| **首页即看板** | 登录首页（Index.razor）是唯一的看板页面，4 张卡片严格 2×2 布局 |
| **链接到功能页** | 每张卡片点击后跳转到已有的功能页面（非独立看板子页面） |
| **无中间层** | 直接在 Index.razor.cs 中调用各业务 Service，无 DashboardService 中间层 |

### 定位

> **首页回答管理层核心问题："今天工厂怎么样？"**
>
> 点击卡片 → 进入对应功能页查看明细，无需在 Dashboard 上下文中重建。

### 与 V2.7 变更说明

V2.7 曾规划 DashboardService 中间层（注入 7 个 Service + AppDbContext），但实际实现采用**更简化**的方式：
- **未创建** DashboardService（Core/Services/API 均无）
- **未创建** Dashboard DTO 目录（DashboardIndexDto/DashboardUrgencyDto 等均不存在）
- Index.razor.cs 直接注入 5 个业务 Service：WorkOrderExecutionService / SectionFlowAnalysisService / FinalInspectionPlanService / NcrService / RepairOrderService
- 无定时自动刷新（30秒 Timer 未实现），手动刷新或切换页面重新加载

- 每个卡片标题右侧有"详情 →"链接跳转到对应功能页面
- **无定时自动刷新**，首次加载时拉取所有数据

### 卡片 1：工单执行

| 项目 | 说明 |
|------|------|
| 数据源 | `WorkOrderExecutionService.GetDashboardSummaryAsync()` |
| 数据结构 | 3 行（原料锁定 / 生产在产 / 成品检验），2 列（合计、急单合计） |
| 合计列 | 该阶段下所有工单的工单数/总重量（吨） |
| 急单合计列 | 蓝色 #1565C0 高亮，仅统计 A+急 + A急 的工单数/重量（吨） |
| 底部合计行 | 3 阶段汇总 |
| 行点击 | 每个阶段名可点击跳转对应页面：原料锁定→/raw-material-lock-plan，生产在产→/batch-plans，成品检验→/final-inspection-plan |
| 详情按钮 | 跳转到 `/workorder-execution` |

**BuildCrossTable 逻辑：**
1. 调用 `GetDashboardSummaryAsync()` 获取 `List<WorkOrderExecutionDashboardItem>`（含 ScheduleStage/UrgencyLevel/OrderCount/TotalWeight）
2. 按 ScheduleStage 分组（1=原料锁定/2=生产在产/3=成品检验）
3. 每组内：合计 = SUM(OrderCount)/SUM(TotalWeight)，急单 = SUM 条件为 UrgencyLevel in ("A+急","A急")
4. 重量格式化为吨，保留 1 位小数

### 卡片 2：批次生产（工段流转分析）

| 项目 | 说明 |
|------|------|
| 数据源 | `SectionFlowAnalysisService.GetAnalysisAsync()` |
| 数据处理 | 对原始 14 个类别（A-N）做合并视图 |
| 合并规则 | A+B+C → **荒管抛修**（待产总量/重点批吨相加，状态取最严重者） |
| | D、E 保持不变 |
| | F+G+H → **固矫切**（待产总量/重点批吨相加，状态取最严重者） |
| | I～N 保持不变 |
| 状态判定(合并组) | 任一类"过多"→ 红色 Error；否则任一类"偏少"→ 橙色 Warning；否则"正常" |
| 列排序 | 支持按 段落类别/待产总量/状态/重点批/吨 排序（点击表头切换升降序） |
| 汇总行 | 待产总量合计 + 重点批/吨合计 |
| 详情按钮 | 跳转到 `/batch-plans` |

**BuildMergedView 逻辑：**
1. 从 API 获取全量 14 个类别 A-N
2. 创建 lookup 字典（CategoryCode → SectionFlowAnalysisDto）
3. 依次构建：荒管抛修(M1) → D → E → 固矫切(M2) → I～N
4. 合并行的 PendingTotal/KeyBatchCount/KeyBatchWeight 取 SUM
5. 合并行的 StatusJudgment 由 MergeStatus() 判定

### 卡片 3：质量检验

| 项目 | 说明 |
|------|------|
| 数据源 | `FinalInspectionPlanService.GetKanbanAsync()` + `NcrService.GetPendingChecksAsync()` + `NcrService.GetAllAsync()` |
| 成品检验 | 3 列：（待到料 / 待检验 / 检验中），每列显示总数（X批/Y吨）和紧急数（X批/Y吨） |
| 紧急定义 | UrgencyLevel = A+急 或 A急 |
| 成检计划链接 | 与"成品检验"标签同行右侧 |
| 不合格报告 | 2 列：待处理批次（待处理批次数）/ 处理中（Status=Pending/Processing 的 NCR 总数） |
| NCR 列表链接 | 与"不合格报告"标签同行右侧 |
| 详情按钮 | 成检计划→`/final-inspection-plan`，NCR列表→`/ncrs` |

**LoadCard3Async 逻辑：**
1. 成品检验：调用 `GetKanbanAsync()` 获取全量计划数据 → 按 KanbanStage 分组（待到料/待检验/检验中）
2. 每组统计 Count + CurrentValidWeight/1000(吨)
3. 紧急统计：额外筛选 UrgencyLevel in ("A+急","A急")
4. 待处理批次：调用 `GetPendingChecksAsync()` 获取待处理批次数
5. 处理中：调用 `GetAllAsync()` filter Status in ("Pending","Processing") 取 TotalCount

### 卡片 4：设备维修

| 项目 | 说明 |
|------|------|
| 数据源 | `RepairOrderService.GetAllListAsync()` |
| 左侧 | 大号红色数字显示在修设备数（RepairStatus != "Completed"） |
| 右侧 | 3 列表格：设备区域 / 设备名称 / 报修时间(MM-dd HH:mm) |
| 排序 | 按报修时间降序 |
| 详情按钮 | 跳转到 `/repair-orders` |

**LoadCard4Async 逻辑：**
1. 调用 `GetAllListAsync()` 获取全量维修工单
2. 筛选 `RepairStatus != "Completed"`（含 Pending 和 InProgress）
3. 按 ReportTime 降序排列

## 3. 数据源依赖汇总

| 卡片 | 数据 | 来源 Service | 目标页面 |
|------|------|-------------|---------|
| 1 | 各阶段工单数/重量/急单数 | WorkOrderExecutionService | /workorder-execution |
| 2 | 工段流转量分析(合并视图) | SectionFlowAnalysisService | /batch-plans |
| 3 | 成检计划三阶段统计 | FinalInspectionPlanService | /final-inspection-plan |
| 3 | 不合格(NCR)待处理/处理中 | NcrService | /ncrs |
| 4 | 在修设备明细 | RepairOrderService | /repair-orders |

## 4. 哪些页面不需要

以下看板子页面**不需要建立**，因为已有功能页面可以直接链接：

| 原计划子页面 | 原因 | 替代链接 |
|-------------|------|---------|
| 交期预警看板 | 已有排程计划页面（SchedulingPlans），含完整的交期筛选和排序 | `/scheduling-plans` |
| 日产量看板 | 大屏场景需要时可考虑，但先不做 | `/batch-plans`（批次维度看产量） |
| 工段负荷看板 | 已有 SectionProductionStatus 页面 | `/section-production-status` |
| 合格率看板 | 已有不合格报告页面 | `/quality/ncr` |
| 设备状态看板 | 已有维修工单列表 | `/repair-orders` |

### 大屏场景（暂不实现）

如果未来有车间大屏需求，可直接全屏打开功能页面（F11），或新增独立大屏页面挂在大屏专用主机上，不走 Index 看板。

## 5. 目录结构

```
MES.Blazor
  ├─ Pages
  │    ├─ Index.razor                   ← 首页（严格 2×2 看板布局）
  │    └─ Index.razor.cs                ← 直接注入 5 个 Service，无中间层
  └─ Services                           ← 直接使用各业务 Service
       ├─ WorkOrderExecutionService.cs
       ├─ SectionFlowAnalysisService.cs
       ├─ FinalInspectionPlanService.cs
       ├─ NcrService.cs
       └─ RepairOrderService.cs
```

## 6. 依赖的实体

所有数据均来自现有上下文，Dashboard 不需要新增 Entity。

### 引用到的外部 Service

| Service | 所属上下文 | 用途 |
|---------|-----------|------|
| WorkOrderExecutionService | 工单 | 工单执行阶段汇总 |
| SectionFlowAnalysisService | 计划排程 | 工段流转量分析 |
| FinalInspectionPlanService | 计划排程 | 成检计划三阶段 |

| RepairOrderService | 设备 | 在修设备明细 |
